# 中級編 Part 3：地図検索・ルート表示アプリ 受入チェックリスト

- 対象仕様：`docs/intermediate/part03-map-route/part03-map-route-spec.md`
- 対象アプリ（将来）：`apps/intermediate/part03-map-route/`
- 判定方法：各項目を実際のブラウザで操作し、期待結果をすべて満たせば合格

---

## 0. 実施方法

### 0.1 前提

- 原則としてChromeまたはEdgeの現行安定版で、GitHub Pages相当のHTTPS環境またはlocalhostから実施する。
- Geoapify側で試験元originだけを許可した公開用ブラウザキーを `config.js` に設定する。
- 開発者ツールのConsole、Network、Application、Elements、Accessibilityを確認できる状態にする。
- 位置情報の許可、拒否、タイムアウトをブラウザ設定またはDevToolsで切り替えられるようにする。
- 通常系では通信可能な状態を使い、異常系ではNetwork request blocking、オフライン、モック、DevTools等で条件を再現する。
- 検索APIの結果や経路は外部データ更新により変わり得るため、候補名や距離の固定値ではなく、選択地点、応答値、画面表示の整合で判定する。
- 各項目の操作中に、Consoleへアプリ由来の未捕捉例外が出ていないことも確認する。

### 0.2 記録欄

各チェックボックスに結果を記録する。失敗時はブラウザ、画面幅、公開origin、検索語、選択候補、移動手段、操作、期待結果との差、HTTPステータス、Console出力を記録する。APIキーと正確な現在地座標は記録しない。

## B. 出発地・目的地検索

- [ ] **B-01 ボタンによるA検索**

  **操作：** 出発地へ具体的な住所または施設名を入力し、A側の「検索」を押す。

  **期待結果：** A検索だけが開始され、処理中表示と二重実行防止が働き、最大5件の候補が表示される。検索中も確定済みBは変わらない。
- [ ] **B-02 EnterによるB検索**

  **操作：** 目的地へ具体的な住所または施設名を入力し、入力欄でEnterを押す。

  **期待結果：** B検索だけが1回実行され、候補が表示され、フォーム送信によるページ再読み込みが起きない。
- [ ] **B-03 入力中は通信しない**

  **操作：** Networkを記録しながら検索入力へ文字入力、貼り付け、削除、IME変換を行い、検索ボタンもEnterも実行しない。

  **期待結果：** Geocoding APIへの要求は1件も送信されない。
- [x] **B-04 1件でも自動確定しない**

  **操作：** 結果が1件になる具体的な検索を実行し、候補を選ばず待つ。

  **期待結果：** 1候補が表示されるがAまたはBは未確定のままで、マーカーも勝手に追加されない。
- [x] **B-05 複数・同名候補**

  **操作：** 同名施設または曖昧な地名を検索する。

  **期待結果：** 複数候補である案内、主要名称、住所・地域等の補足が表示され、先頭候補へ自動確定しない。
- [ ] **B-06 候補選択**

  **操作：** A候補を1件選び、続けてB候補を1件選ぶ。

  **期待結果：** 選んだ候補だけが各地点へ確定し、確定名とA・Bマーカーが更新され、対象地点が見える位置へ地図が移動する。両地点確定後は両方が画面内に収まる。
- [ ] **B-07 検索入力と確定地点の分離**

  **操作：** Aを確定後、A検索入力だけを書き換える。

  **期待結果：** 新候補を選ぶまで確定済みA、Aマーカー、既存Bは変わらない。
- [ ] **B-08 検索語の検証**

  **操作：** 空白だけ、および前後空白除去後201文字の検索語で検索する。

  **期待結果：** それぞれ具体的な入力エラーが表示され、Geoapifyへ要求しない。
- [ ] **B-09 地点カードの簡潔な検索表示**

  **操作：** A/Bカードをマウス、キーボード、スクリーンリーダーで確認し、各入力からボタン操作とEnter操作を行う。

  **期待結果：** 見出しと補足は同じ行で自然に折り返し、可視ラベルと操作ヘルプの重複がない。labelとinput、入力エラーの関連は維持され、双方の可視ボタンは「検索」、アクセシブル名はそれぞれ「出発地Aを検索」「目的地Bを検索」である。
- [x] **B-10 初期中心付近のB候補を優先**

  **操作：** A、B、現在地を未設定の初期地図で「セブンイレブン」をB検索し、Networkと候補を確認する。

  **期待結果：** `bias=proximity:141.3545,43.0618` が送信され、札幌市中心部付近の候補が上位に表示される。最大5件から利用者が選択するまでBは確定しない。
- [x] **B-11 Aまたは現在地付近のB候補を優先**

  **操作：** 現在地をAへ設定して「セブンイレブン」をB検索し、続けて東京の地点をAへ確定して同じ検索を行う。

  **期待結果：** 前者は現在地、後者は東京のA座標が経度・緯度順のbiasとして各要求に固定され、それぞれ基準地点付近の候補が上位に表示される。
- [x] **B-12 B付近のA候補を優先**

  **操作：** Bを確定後、一般的な施設名をA検索してNetworkと候補を確認する。

  **期待結果：** 確定済みBの経度・緯度がbiasとなり、B付近の候補が上位に表示される。現在地や地図中心よりBが優先される。
- [x] **B-13 biasは地域を制限しない**

  **操作：** 札幌市中心のbiasが使われる状態で「セブンイレブン 福岡」を検索する。

  **期待結果：** `filter` は送信されず、福岡の候補を取得できる。日本国内限定処理や候補の自動確定がない。
- [ ] **B-14 biasパラメーターと検索中スナップショット**

  **操作：** Networkで地点検索要求を確認し、応答を遅延させた状態で地図移動、現在地変更、反対側地点変更を行う。

  **期待結果：** `text`、`format=geojson`、`lang=ja`、`limit=5`、`apiKey`に加え、有効な場合だけ`bias=proximity:経度,緯度`が1つ送信される。進行中要求のbiasは途中で変わらず、既存のAbortControllerとrequestIdにより古い応答を採用しない。

  **操作：** 該当結果がない検索語を実行する。

  **期待結果：** 候補0件と検索語を具体化する案内が表示され、地点は自動確定されず、反対側の確定地点は維持される。
- [ ] **C-02 ネットワークエラー**

  **操作：** 有効な地点を確定した後、オフライン等で別の検索を実行する。

  **期待結果：** 通信失敗と再試行案内が表示され、処理中状態が解除され、既存の確定地点は維持される。
- [ ] **C-03 HTTP 401／403**

  **操作：** 無効キーまたは許可されていないoriginで検索する。

  **期待結果：** HTTPエラーとキー設定・利用元制限の確認案内が表示され、キー値、要求URL全体、応答本文は画面やConsoleへ出ない。

## D. 現在地

- [x] **D-01 明示操作のみ**

  **操作：** ページを開き、現在地ボタンを押さずに検索と地図操作を行う。

  **操作：** DevToolsで既知の位置を設定し、「現在地を出発地に設定」を押して許可する。

- [ ] **D-02a 現在地と検索地点Aの分離表示**

  **操作：** D-02の後、検索候補から現在地とは別の地点をAへ設定する。

  **期待結果：** 現在地の内部状態は維持され、複合マーカーが消え、現在地マーカーと検索地点のAマーカーが別々に表示される。

- [ ] **D-05 利用拒否**

  **操作：** 位置情報を拒否する。

  **期待結果：** 拒否された旨とブラウザ設定または検索利用を案内し、取得中状態を解除し、既存地点を維持する。
- [ ] **D-06 タイムアウト**

  **操作：** 位置取得が10秒以内に完了しない条件を作る。

  **期待結果：** タイムアウトと再試行または検索利用を案内し、アプリを継続操作できる。
- [ ] **D-07 その他の取得失敗**

  **操作：** `POSITION_UNAVAILABLE` 等を発生させる。

  **期待結果：** 現在地取得失敗が通知され、既存のA、B、経路に関係しない状態が維持される。

## E. 直線距離

- [ ] **E-01 Haversine計算**

  **操作：** DevToolsで緯度経度が既知の現在地を取得し、既知座標のBを選ぶ。画面値を地球半径6,371,000mのHaversine式による手計算値と比較する。

  **期待結果：** 1,000m未満は10m単位、1,000m以上は0.1km単位の四捨五入規則で一致する。
- [ ] **E-02 10m未満表示**

  **操作：** 現在地から10m未満のBを設定する。

  **期待結果：** 「直線距離 10 m未満」と表示される。
- [ ] **E-03 表示条件**

  **期待結果：** 現在地とBが両方ある期間だけ直線距離が表示され、それ以外は未計算または理由が表示される。
- [ ] **E-04 経路距離との区別**

  **操作：** 現在地をAに設定し、Bへの経路を作成する。

  **期待結果：** 「現在地から目的地Bの直線距離」と「Geoapifyによる経路距離」が別ラベルで表示され、概算と経路値を誤認しない。

## F. ルート検索

- [ ] **F-01 徒歩ルート**

  **操作：** 10mより離れたA・Bを確定し、徒歩を選び「ルートを検索」を押す。

  **期待結果：** 検索中表示と二重実行防止の後、徒歩経路が1本表示され、経路距離、推定所要時間、徒歩の表示があり、A・B・経路全体が地図内に収まる。
- [ ] **F-02 車ルート**

  **操作：** 同じA・Bで車を選び、ルートを検索する。

  **期待結果：** 旧徒歩経路が残らず車経路1本へ置き換わり、表示値は最新API応答のdistance・timeを仕様の単位へ丸めた値と一致する。
- [ ] **F-03 API要求形式**

  **操作：** 徒歩と車でNetwork requestを確認する。

  **期待結果：** `api.geoapify.com/v1/routing` へAの緯度・経度、Bの緯度・経度の順でwaypointsが送られ、modeはそれぞれ `walk`、`drive`、formatは `geojson` である。
- [ ] **F-04 地点不足**

  **操作：** Aだけ、Bだけ、両方なしの各状態を順に作り、「ルートを検索」ボタン付近とNetworkを確認する。

  **期待結果：** 各状態で「ルートを検索」は `disabled` になり、ボタン付近に不足しているA、B、または両方が具体的に示され、Routing APIを呼ばない。
- [ ] **F-05 実質的同一地点**

  **操作：** Haversine距離が10m以下のA・Bを設定してルート検索する。

  **期待結果：** 実質的に同一地点である旨と変更案内が表示され、Routing APIを呼ばない。
- [ ] **F-06 ルートなし**

  **操作：** モックまたは到達不能な地点で、有効なroute Featureがない応答を発生させる。

  **期待結果：** ルートが見つからない旨と地点・移動手段の変更を案内し、経路線と経路結果は未計算になり、A・B・現在地・直線距離は維持される。
- [ ] **F-07 Routing API応答形式不正**

  **操作：** geometry、distance、timeのいずれかが欠けるか不正な応答を返す。

  **期待結果：** API応答形式不正として経路を部分採用せず、未捕捉例外がなく再試行できる。
- [ ] **F-08 ルートHTTP・ネットワークエラー**

  **操作：** 経路検索でネットワーク失敗、HTTP 403、429を順に発生させる。

  **期待結果：** 各原因に応じた回復案内があり、キーや応答本文を表示せず、A・Bと直線距離を維持する。
- [x] **F-09 初回の移動手段変更**

  **操作：** A・Bを設定し、まだルート検索を実行せずに徒歩から車へ変更してNetworkを確認する。

  **期待結果：** ルート検索は自動実行されず、Routing API要求がない。初回は手動の「ルートを検索」が必要である。
- [x] **F-10 手動検索後の徒歩から車**

  **操作：** 徒歩ルートを手動検索した後、車へ変更する。

  **期待結果：** 旧徒歩経路と結果が直ちに無効化され、「車のルートを更新しています…」の後、重複のない1回のRouting API要求で車ルート、距離、所要時間、移動手段が画面へ同時に表示される。
- [x] **F-11 車から徒歩への自動更新**

  **操作：** F-10に続けて徒歩へ戻す。

  **期待結果：** 「徒歩のルートを更新しています…」の後、徒歩ルートが自動取得され、経路線、距離、所要時間、結果カードの移動手段が徒歩に一致する。
- [x] **F-12 素早い連続変更**

  **操作：** ルート検索実行済みの同じA/Bで、徒歩、車、徒歩を応答前に素早く切り替える。

  **期待結果：** 進行中の旧要求が中断または無効化され、最後の徒歩だけが表示される。loading、aria-busy、ボタン状態が最新要求と一致し、AbortErrorを通知しない。
- [x] **F-13 地点変更後の初回状態**

  **操作：** ルート検索後にAまたはBを別候補へ変更し、移動手段を変更する。

  **期待結果：** 自動検索せず、変更後の地点条件で手動検索を一度実行するまでRouting API要求がない。
- [x] **F-14 経路クリア後の初回状態**

  **操作：** ルート検索後に「経路をクリア」を押し、移動手段を変更する。

  **期待結果：** 自動検索せず、Routing API要求がない。手動検索は引き続き利用できる。
- [ ] **F-15 地点全クリア後の初回状態**

  **操作：** ルート検索後に「地点をすべてクリア」を押し、地点を再設定して移動手段を変更する。

  **期待結果：** 自動検索せず、新しい地点条件で手動検索が必要になる。
- [ ] **F-16 自動更新失敗後の再試行**

  **操作：** 手動検索後の移動手段変更で自動検索を失敗させ、処理終了後に「ルートを検索」を押す。

  **期待結果：** 失敗理由が通知され、操作可能状態へ戻り、手動ボタンから同じ現在条件で再試行できる。
