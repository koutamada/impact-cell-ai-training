## 1. 目的と対象範囲

### 1.1 目的 `[必須A]`

住所や施設名から出発地と目的地を指定し、現在地との直線距離、および徒歩・車の経路、経路距離、推定所要時間を1画面で確認できる地図アプリを作成する。地図、検索候補、位置情報、経路APIという複数の非同期情報を安全に統合することを学習目的とする。

### 1.2 対象利用者 `[必須A]`

- 住所または施設名を使って2地点間の経路を調べたい利用者
- 現在地を出発地として目的地までの概略を確認したい利用者
- マウス、タッチ、またはキーボードで主要操作を行う利用者

### 1.3 課題クリア条件 `[必須A]`

| クリア条件 | 本書の対応箇所 |
| --- | --- |
| 地図を表示し、拡大、縮小、ドラッグ移動できる | 6章 |
| 住所・施設を検索し、候補から地点を選択できる | 7章 |
| 出発地Aと目的地Bを指定し、識別可能なマーカーを表示できる | 8章 |
| 現在地を取得し、出発地に設定できる | 9章 |
| 現在地と目的地の直線距離をJavaScriptで計算できる | 10章 |
| 徒歩または車の経路、距離、推定所要時間を表示できる | 11章 |
| 入れ替え、経路クリア、地点クリアができる | 8章、11章 |
| 非同期処理の進行、二重実行、競合、異常系を扱える | 5章、13章 |

### 1.4 MVP範囲 `[必須A]`

- 単一の出発地Aと単一の目的地Bを扱う。
- 地点は検索候補選択または現在地取得によって確定する。
- 移動手段は徒歩と車の2種類に限定する。
- 経路はGeoapify Routing APIが返す1経路だけを表示する。
- 状態はページ内のメモリだけで管理し、再読み込み後に復元しない。

## 3. 画面構成

### 3.1 全体構成 `[必須A]`

上から次の順に配置する。

1. ヘッダー
2. 地点・経路操作領域
3. 地図領域（見出し内の全体通知を含む）
4. 距離・経路結果領域
5. ライセンス・データ帰属表示

広い画面では地点・経路操作と地図を見比べやすい2列構成としてよい。操作パネル内は全幅で見出し、出発地A、目的地B、経路操作領域の順に縦配置する。DOM順は操作領域、地図、結果の順を基本とし、CSSだけで視覚配置を調整する。

### 3.2 ヘッダー `[必須B]`

- アプリ名「地図検索・ルート表示アプリ」を表示する。
- 住所・施設検索、現在地、経路表示を行うアプリであることを短く説明する。
- Geoapifyへの外部通信があることを隠さず、位置情報は利用者の操作時だけ取得する旨を表示する。
- 幅1101px以上では、1段目の左に補助ラベル、右に横並びのデータ利用バッジを置き、2段目の左にタイトル、右に説明文を置く。1100px以下ではタイトルと説明文を縦配置にする。

### 3.3 地図見出し内の全体通知領域 `[必須B]`

全幅の独立した通知帯は設けず、地図パネルの見出し行へ全体通知領域を配置する。狭い画面では同じ地図見出し内で折り返し、通知文を切り詰めない。

- 成功、案内、警告、エラー、処理中を文字で表示する。
- エラーは色だけでなく「エラー」等の文言または記号を伴わせる。
- 新しい重要通知を支援技術が認識できるよう、適切な `aria-live` を設定する。
- 検索候補の件数変更や地図の連続移動を逐次読み上げず、過剰な通知を避ける。
- APIキーそのもの、APIキーを含むURL、応答の機密になり得る内容は表示しない。

### 3.4 地点検索領域 `[必須A]`

出発地Aと目的地Bそれぞれに次を用意する。

- 常時見えるラベル付き検索入力
- 「検索」ボタン
- 検索中表示
- 候補一覧
- 確定地点名または「未設定」の表示

出発地側には「現在地を出発地に設定」ボタンを設ける。検索入力と確定地点は区別し、入力文字の変更だけで確定地点を変更しない。

- A/B地点カードはすべての画面幅でA、Bの順に縦配置する。
- A/B入れ替えボタンはAカードとBカードの間へ中央揃えでコンパクトに配置し、地点の上下方向の入れ替えを示す「⇅」を表示する。カード内容を覆わず、ボタンのためだけに大きな縦余白を設けない。
- デスクトップでは各カード内の検索入力と検索ボタンを横一列にし、狭い画面では必要に応じて縦配置する。
- A側だけに現在地ボタンを置き、B側へ意味のない空要素や説明を追加しない。
- カード見出しはA/B記号、見出し、「住所または施設名から選択」の補足を同じ行に置き、狭い幅では自然に折り返す。
- 検索入力のlabelは視覚的に隠して `for` と `id` の関連を維持し、入力欄のアクセシブル名でA/Bを区別する。
- 検索ボタンの可視文言は双方「検索」とし、出発地側は「出発地Aを検索」、目的地側は「目的地Bを検索」のアクセシブル名を付ける。処理中は「検索中…」とする。
- 入力欄のplaceholderは双方「住所または施設名を入力」とし、入力エラーだけを `aria-describedby` で関連付ける。可視状態の検索操作ヘルプは表示しない。

### 3.5 経路操作領域 `[必須A]`

- 移動手段：徒歩、車
- 「ルートを検索」ボタン
- 「AとBを入れ替える」ボタン
- 「経路をクリア」ボタン
- 「地点をすべてクリア」ボタン

ボタンは目的が分かる文言を持つ。利用不能時は `disabled` とし、理由を近接する案内または状態表示で確認できるようにする。

- 「移動手段」のfieldsetではlegendを視覚的に隠してアクセシブル名を維持し、徒歩と車を1行に配置する。
- 入れ替えボタンは `aria-label` と `title` を「出発地Aと目的地Bを入れ替える」とし、44px四方以上のbutton要素とする。地点不足時の `disabled` と明瞭なキーボードフォーカスを維持する。
- 徒歩と車は1行の幅を均等に使用し、ルート検索ボタンはその直下に配置する。

- 出発地Aまたは目的地Bの一方でも未設定なら「ルートを検索」を `disabled` にする。
- ボタン付近には「出発地Aと目的地Bを設定してください」「目的地Bを設定してください」等、利用不能な理由がある場合だけ表示する。利用可能時は案内要素を非表示にし、余白を残さない。
- A・Bが揃っていてもAPIキー未設定、2地点が10m以内、または経路検索中ならボタンを無効にし、その時点の主な理由を表示する。理由がある場合だけ `aria-describedby` でボタンと関連付ける。

### 3.6 地図領域 `[必須A]`

- Leafletの地図、ズームコントロール、A・B・現在地マーカー、経路線を表示する。
- 地図コンテナにはデスクトップと375pxの双方で操作できる明示的な高さを与える。
- 地図を利用できない場合も、検索入力、確定地点、結果、エラー文が確認できる構造にする。
- 地図上の帰属表示を常時表示し、コントロールや他要素で覆わない。
- 地図の表示高は、幅1201px以上で約440px、801〜1200pxで約420px、521〜800pxで約380px、520px以下で約300pxとする。

### 3.7 結果領域 `[必須A]`

- 現在地から目的地Bまでの直線距離
- 出発地Aから目的地Bまでの経路距離
- 推定所要時間
- 選択中の移動手段

直線距離と経路距離は見出しと説明で明確に区別する。値がない場合は空欄にせず「未計算」または計算できない理由を表示する。

## 4. データモデル

### 4.1 地点オブジェクト `[必須B]`

```js
{
  id: "Geoapifyのplace_idまたはアプリ内で生成した識別子",
  label: "画面表示用の地点名または住所",
  latitude: 43.0618,
  longitude: 141.3545,
  source: "search" // "search" | "geolocation"
}
```

- `label` は空でない文字列とする。
- `latitude` は有限数かつ `-90` 以上 `90` 以下、`longitude` は有限数かつ `-180` 以上 `180` 以下とする。
- API応答のプロパティをオブジェクトごと保持せず、必要な値だけをコピーする。
- 現在地の `id` はアプリ内で生成し、APIキーや位置情報の生データを含めない。

### 4.2 検索候補 `[必須B]`

```js
{
  id: "候補を識別する文字列",
  label: "formatted等から作る主要表示",
  supplementalLabel: "市区町村・都道府県・国・種別等の補足",
  latitude: 43.0,
  longitude: 141.0
}
```

- GeoJSON `FeatureCollection` の各 `Feature` から最大5件を構築する。
- `properties.formatted`、`properties.lat`、`properties.lon` を基本とし、不足時は有効な `geometry.coordinates` を代替利用できる。
- 必須値が不正な候補は除外する。全候補が不正ならAPI応答形式不正とする。
- ラベルは重複し得るため、補足情報と候補順を表示して利用者が区別できるようにする。

### 4.3 経路オブジェクト `[必須B]`

```js
{
  mode: "walk", // "walk" | "drive"
  geometry: {},
  distanceMeters: 1234.5,
  durationSeconds: 900,
  origin: { latitude: 43.0, longitude: 141.0 },
  destination: { latitude: 43.1, longitude: 141.1 }
}
```

- `geometry` はLeafletで線として描画できる有効なGeoJSON geometryとする。
- 距離と所要時間は有限かつ0以上でなければならない。
- 経路作成時の地点座標と移動手段を保持し、現在状態と一致する経路だけを有効とする。

## 5. 状態管理と競合制御

### 5.1 アプリケーション状態 `[必須B]`

```js
{
  origin: null,
  destination: null,
  currentLocation: null,
  candidates: { origin: [], destination: [] },
  queries: { origin: "", destination: "" },
  travelMode: "walk",
  routeComparisonActive: false,
  route: null,
  straightDistanceMeters: null,
  loading: {
    originSearch: false,
    destinationSearch: false,
    geolocation: false,
    route: false
  },
  errors: {
    global: null,
    originSearch: null,
    destinationSearch: null,
    geolocation: null,
    route: null,
    tiles: null
  },
  requestIds: {
    originSearch: 0,
    destinationSearch: 0,
    route: 0,
    geolocation: 0
  }
}
```

Leafletのmap、marker、tile layer、route layer、AbortControllerは画面資源として別に保持し、永続化対象にしない。

### 5.2 状態変更の原則 `[必須B]`

- 検索入力の変更は `queries` だけを更新し、確定済み地点を暗黙に変更しない。
- 候補選択または現在地設定が成功した時点で地点を確定する。
- AまたはB、移動手段が変わったら、既存経路、経路距離、所要時間、経路線を直ちに無効化して削除する。
- `routeComparisonActive` は、利用者が手動ルート検索を開始し、同じ地点の方向違いまたは移動手段違いを比較しているページ内状態を表す。初期値は `false` で、初回の手動検索開始時に `true` とする。経路表示データ `route` の有無とは独立させ、自動更新中や一時的な検索失敗でも維持する。
- A/B候補から別地点を確定した場合、現在地を新しくAへ設定した場合、経路クリア、地点全クリアでは `routeComparisonActive` を `false` に戻す。移動手段変更とA/B入れ替えでは `true` を維持する。
- 経路線・距離・所要時間・経路エラーを消す処理は比較セッションを暗黙に終了しない。地点変更用、明示クリア用、自動更新用で消去する状態を区別する。
- Bまたは現在地が変わったら、直線距離を現在状態から再計算する。いずれかがなければ非表示にする。
- ある処理の失敗によって、関係のない確定済み地点を消さない。
- 画面表示はアプリ状態から更新し、DOMだけに正本を持たない。

### 5.3 AbortControllerとrequestId `[必須B]`

- 出発地検索、目的地検索、経路検索ごとにAbortControllerと単調増加するrequestIdを持つ。
- 同じ種類の新しい処理を開始すると、直前の未完了リクエストを `abort()` し、requestIdを更新する。
- 中断できない、または中断と応答が競合する場合も、完了時のrequestIdが最新値と一致しなければ結果もエラーも採用しない。
- 地点変更、入れ替え、経路クリア、地点クリア時は実行中の経路リクエストを中断し、古い応答を無効化する。
- 地点クリア時は検索と位置情報取得も無効化し、後着した応答で地点や候補を復活させない。
- 有効な出発地A検索を開始した場合とA候補を選択した場合は、待機中の現在地取得のrequestIdを更新してloading状態を解除する。中断できないGeolocation APIの後着成功・失敗コールバックは採用せず、選択済みのAを上書きしない。
- 現在地取得を開始した場合は、待機中の出発地A検索をAbortControllerで中断し、出発地検索のrequestIdを更新してloading状態と候補を消去する。中断と応答が競合しても、後着した検索応答でA候補を復活させない。
- 上記の排他制御は出発地Aにだけ適用し、目的地B検索のAbortController、requestId、loading状態、候補には影響させない。
- `AbortError` は利用者向けのネットワークエラーとして通知しない。

### 5.4 永続化 `[MVP外]`

地点、検索履歴、候補、現在地、移動手段、経路をlocalStorage、sessionStorage、Cookie、IndexedDBへ保存しない。ページ再読み込み後は初期状態へ戻る。

## 6. 地図とタイル

### 6.1 Leaflet初期化 `[必須A]`

- `window.L` と必要なLeaflet APIの存在を確認してから初期化する。
- 初期中心は札幌市中心部、初期ズームは13とする。
- マウスまたはタッチによるドラッグ移動、ホイールまたはボタンによる拡大縮小を利用できるようにする。
- Leaflet初期化失敗は捕捉し、地図を利用できない旨を通知する。他の説明や設定案内までクラッシュさせない。

### 6.2 Geoapifyタイル `[必須A][必須B]`

- 通常解像度は `https://maps.geoapify.com/v1/tile/osm-bright/{z}/{x}/{y}.png?apiKey={apiKey}` を使用する。
- Retina環境は `https://maps.geoapify.com/v1/tile/osm-bright/{z}/{x}/{y}@2x.png?apiKey={apiKey}` を使用してよい。
- `maxZoom` は20とする。
- APIキー未設定時はタイル要求を送らず、地図背景を利用できないことと設定方法を通知する。
- `tileerror` を監視し、初回または状態変化時に地図タイル読込失敗を通知する。同じ失敗をタイル枚数分連続通知しない。
- 一部または全部のタイル失敗で確定済み地点や検索結果を消去しない。

### 6.3 ビュー制御 `[必須A]`

- AまたはBを確定したら、対象地点を中心にズーム15で表示する。
- 現在地取得だけが成功した場合も現在地が見える位置へ移動する。
- AとBが揃った時点では両マーカーが収まるよう `fitBounds` する。
- 経路表示時は経路線とA・Bが余白付きで収まるよう `fitBounds` する。
- 1点だけ、または全点が実質同座標で有効なboundsを作れない場合は `setView` を使用する。
- viewport変更や非表示領域からの再表示後は必要に応じて `invalidateSize()` を行う。

### 6.4 マーカーと経路レイヤー `[必須A][必須B]`

- Aマーカーは文字 `A`、Bマーカーは文字 `B`、現在地は「現在地」または現在地を示す異なる形を持つ。
- 色に加え、文字、形、アクセシブル名のいずれでも識別できるようにする。
- 現在地を出発地Aへ設定し、`origin` と `currentLocation` が同一座標を表す場合は、Aマーカーと現在地マーカーを重ねず、文字 `A・現在地` を持つ単一の複合マーカーを表示する。
- 複合マーカー表示中も、内部状態の `origin` と `currentLocation` は別々の地点オブジェクトとして保持する。
- その後Aを別の検索地点へ変更した場合は、複合マーカーを削除し、検索地点のAマーカーと保持中の現在地マーカーを別々に表示する。
- 新しい経路を採用する前に古い経路レイヤーを削除し、複数経路線を残さない。
- 経路線は背景地図上で判別可能な太さとコントラストを持つ。

## 7. 住所・施設検索

### 7.1 検索開始 `[必須A]`

- API呼び出しは「検索」ボタンまたは検索入力でのEnterに限る。
- 文字入力、貼り付け、IME変換のたびにAPIを呼ばない。
- 前後空白を除去した検索語が0文字または200文字超ならAPIを呼ばず、入力エラーを表示する。
- 出発地検索と目的地検索は独立して実行できる。
- 検索開始時に同じ欄の旧候補と旧検索エラーを消し、確定済み地点は維持する。

### 7.2 Geoapify Geocoding API `[必須A][必須B]`

- `GET https://api.geoapify.com/v1/geocode/search` を使用する。
- クエリは `text`、`format=geojson`、`lang=ja`、`limit=5`、`apiKey` とする。
- 検索語は `URLSearchParams` 等で正しくURLエンコードする。
- 検索開始時に有効な基準座標がある場合は `bias=proximity:経度,緯度` を追加し、候補順位を基準地点の近隣優先にする。Routing APIの座標順とは逆であることに注意する。
- B検索の基準地点はA、現在地、Leaflet地図中心、札幌市初期中心の順とする。A検索ではB、現在地、Leaflet地図中心、札幌市初期中心の順とする。
- 基準座標は有限数および緯度経度範囲を検証し、検索開始時のスナップショットとして固定する。不正な場合は次の優先候補を使用し、いずれも有効でなければbiasなしで通常検索を継続する。
- biasは順位付けだけに使用し、`filter` による地域制限は設けない。「セブンイレブン 福岡」等の明示的な地域を近隣優先だけで排除せず、日本国内にも限定しない。
- 国や範囲による固定フィルターは設けず、世界の住所・施設名を検索対象とする。
- HTTP成功だけでなく、トップレベルがGeoJSON `FeatureCollection`、`features` が配列、各採用候補のラベルと座標が有効であることを検証する。

### 7.3 候補表示と確定 `[必須A]`

- 有効候補が1件でも、利用者の選択前に地点へ自動確定しない。
- 各候補をボタン等のキーボード操作可能な要素として表示する。
- 候補には主要ラベルと、取得できる範囲で市区町村、都道府県、国、種別等の補足を表示する。
- 複数候補または同名候補がある場合は「複数の候補があります。住所を確認して選択してください」等の案内を表示する。
- 候補選択時に対応するAまたはBだけを確定し、候補一覧を閉じ、確定名とマーカーを更新する。
- 候補選択で別側の確定地点を変更しない。

### 7.4 0件と曖昧な結果 `[必須B]`

- `features` が空なら「該当する候補がありません。住所や施設名を具体的にしてください」等を表示する。
- 複数件や同名結果はエラーで全件破棄せず、補足付き候補一覧で利用者の判断を求める。
- APIが信頼度を返しても、信頼度だけを根拠に自動確定しない。

## 8. 地点操作

### 8.1 出発地A・目的地B `[必須A]`

- AとBは別の検索欄、候補一覧、確定表示、マーカーを持つ。
- 同じ検索候補を両方へ選ぶこと自体は許可するが、経路検索時に10m以下なら実質的に同一として拒否する。
- 地点確定後も検索入力を編集できるが、新候補を選ぶまで確定値は変わらない。

### 8.2 入れ替え `[必須A]`

- AとBが両方確定している場合だけ実行できる。
- 地点オブジェクト、確定名、入力表示、マーカーの役割を同時に入れ替える。
- 既存経路、経路距離、所要時間、経路エラーを削除する。`routeComparisonActive` が有効で自動更新条件を満たす場合は、入れ替え後のAからBへ自動経路検索する。比較セッション開始前は自動検索しない。
- 現在地状態は入れ替えない。直線距離は現在地と新しいBで再計算する。
- 実行中の検索・経路の古い応答が入れ替え後を上書きしないよう無効化する。

### 8.3 経路クリア `[必須A]`

- 経路線、経路距離、所要時間、経路エラーを削除する。
- A、B、現在地、検索入力、移動手段、直線距離は維持する。
- 実行中の経路検索を中断し、後着応答を無視する。

### 8.4 地点をすべてクリア `[必須A]`

- A、B、現在地、各入力、候補、全マーカー、直線距離、経路、経路結果、関連エラーを初期状態へ戻す。
- 移動手段は初期値の徒歩へ戻す。
- 実行中の検索、位置情報取得、経路検索を無効化し、後着応答を採用しない。
- 地図を札幌市中心部、ズーム13へ戻す。

## 9. 現在地

### 9.1 取得開始 `[必須A]`

- 「現在地を出発地に設定」を利用者が実行した場合だけ `navigator.geolocation.getCurrentPosition` を呼ぶ。
- ページ表示直後や別操作時に許可を要求しない。
- オプションは `enableHighAccuracy: false`、`timeout: 10000`、`maximumAge: 0` とする。
- 開始時に待機中の出発地A検索を中断・無効化し、A候補と出発地検索のloading状態を消去する。目的地B検索は維持する。
- 取得中は状態を文字で示し、同じ取得ボタンを無効化して二重実行を防ぐ。

### 9.2 取得成功 `[必須A][必須B]`

- 緯度経度を範囲検証し、有効なら `currentLocation` と `origin` の両方を更新する。
- Aのラベルは「現在地」とし、Aマーカーと現在地マーカーの意味が確認できるようにする。
- 既存のBは維持する。既存経路は削除し、Bがあれば直線距離を計算する。
- 地図を現在地へ移動し、Bもある場合は両地点が見えるよう調整する。
- 正確な緯度経度を通常の画面やConsoleへ表示しない。必要な地図表示と距離計算にだけ使用する。
- 取得待機中に有効なA検索が開始された、またはA候補が選択された場合、後着した成功結果でAを上書きしない。

### 9.3 取得失敗 `[必須B]`

| 条件 | 表示と状態 |
| --- | --- |
| `navigator.geolocation` 非対応 | 現在地機能を利用できない旨と、検索でAを設定できる旨を表示する |
| `PERMISSION_DENIED` | 位置情報が拒否された旨と、ブラウザ設定または検索利用を案内する |
| `TIMEOUT` | 10秒以内に取得できなかった旨と再試行または検索利用を案内する |
| `POSITION_UNAVAILABLE` またはその他 | 現在地を取得できなかった旨と再試行または検索利用を案内する |

失敗時は既存のA、B、経路に関係しない状態を維持し、未捕捉例外を出さない。

## 10. 直線距離

### 10.1 計算条件 `[必須A]`

- `currentLocation` と目的地Bの両方がある場合だけ計算する。
- Aが検索地点であっても、現在地が別に保持されBがあれば「現在地からB」の距離として計算する。
- 現在地未取得またはB未設定なら直線距離を表示しない。
- APIへ距離計算を依頼せずJavaScriptで計算する。

### 10.2 Haversine式 `[必須B]`

緯度経度をラジアンへ変換し、地球半径 `R = 6,371,000m` として次を使用する。

```text
Δφ = φ2 - φ1
Δλ = λ2 - λ1
a = sin²(Δφ / 2) + cos(φ1) × cos(φ2) × sin²(Δλ / 2)
c = 2 × atan2(√a, √(1 - a))
d = R × c
```

- 浮動小数点誤差対策として `a` を0〜1へ収めてから平方根を計算する。
- 内部値はメートルの有限数として保持する。

### 10.3 単位と丸め `[必須B]`

- 1,000m未満は10m単位で四捨五入し、`直線距離 約 850 m` のように表示する。
- 1,000m以上はkmへ変換し、小数第1位で四捨五入し、`直線距離 約 3.2 km` のように表示する。
- 10m未満は `直線距離 10 m未満` と表示する。
- 「直線距離」「現在地から目的地B」「概算」の文言を含め、経路距離と誤認させない。

## 11. ルート検索

### 11.1 検索条件 `[必須A][必須B]`

- AとBが確定し、移動手段が徒歩または車で、APIキーが設定済みの場合だけ実行できる。
- AまたはBが未設定の場合は「ルートを検索」を `disabled` にし、ボタン付近へ不足している地点を具体的に表示する。無効ボタンの操作を前提とせず、状態変更のたびに案内を更新する。
- 地点不足状態ではRouting APIを呼ばない。
- AとBのHaversine距離が10m以下なら、実質的に同一地点としてAPIを呼ばず変更を促す。
- 実行中は「ルートを検索」を無効にして二重実行を防ぐ。
- ルート検索ボタン付近の理由表示は、地点不足、APIキー未設定、2地点が10m以内、検索中等でボタンが無効な場合だけ表示する。実行可能時は要素を非表示にして余白を残さず、`aria-describedby` も設定しない。
- ページ表示直後およびA/Bを設定しただけの状態では、移動手段を変更しても自動検索しない。初回は利用者が「ルートを検索」を実行する。
- `routeComparisonActive` が `true` の間は、checked状態が実際に別の移動手段へ変わった場合に限り、旧経路と結果を直ちに無効化し、新しい移動手段で自動検索する。変更前に自動検索条件を退避し、移動手段変更用の経路クリアでは比較セッションを維持する。検索失敗後も同様に自動再試行できる。
- A/B未設定、2地点が10m以内、APIキー未設定では自動検索しない。
- 自動検索中も手動ボタンを残し、処理中だけ無効化する。移動手段変更時は「徒歩のルートを更新しています…」または「車のルートを更新しています…」、入れ替え時は「入れ替え後のルートを更新しています…」、成功時は「〜のルートを表示しました。」と通知する。
- 移動手段変更時は進行中の旧経路要求をabortしてrequestIdを更新し、素早い連続変更では最後の選択に一致する応答だけを採用する。`AbortError` は通常のエラーとして通知しない。

### 11.2 Geoapify Routing API `[必須A][必須B]`

- `GET https://api.geoapify.com/v1/routing` を使用する。
- `waypoints` は `Aの緯度,Aの経度|Bの緯度,Bの経度` の順にする。
- 徒歩は `mode=walk`、車は `mode=drive` とする。
- `format=geojson` と `apiKey` を付ける。
- `URLSearchParams` 等でパラメーターを構築する。
- レスポンスはGeoJSON `FeatureCollection`、有効な最初の経路 `Feature`、描画可能なgeometry、有限で0以上の `properties.distance` と `properties.time` を検証する。
- 複数経路が返っても最初の有効経路だけを採用し、代替経路選択UIは設けない。

### 11.3 採用と表示 `[必須A]`

- 最新requestIdかつ現在のA、B、移動手段と一致する応答だけを採用する。
- 古い経路レイヤーを削除してから新しい経路線を1本表示する。
- `properties.distance` を経路距離、`properties.time` を推定所要時間として表示する。
- 経路距離は1,000m未満を10m単位、1,000m以上を0.1km単位で四捨五入する。
- 所要時間は秒を分へ換算して1分単位で四捨五入し、1分未満は「1分未満」、60分以上は「N時間M分」で表示する。
- 「Geoapifyによる経路距離」「推定所要時間」「徒歩」または「車」を文字で示す。
- A、B、経路線全体が見えるよう `fitBounds` する。

### 11.4 ルートなし `[必須B]`

- 有効な経路Featureが0件なら「指定した地点と移動手段ではルートが見つかりません」等を表示する。
- 旧経路を現在の結果として残さず、経路線、経路距離、所要時間を未計算状態にする。
- A、B、現在地、直線距離は維持し、地点または移動手段を変更して再試行できるようにする。

## 12. APIキーと設定

### 12.1 公開前提 `[必須B]`

- GitHub Pagesは静的配信のため、ブラウザが使用するAPIキーを完全には秘匿できない。
- `config.js` に置くキーは、公開されることを前提としたGeoapifyのブラウザ用キーとする。
- Geoapify MyProjects側で、公開するGitHub Pagesのorigin／HTTP referrer／CORS等、提供される利用元制限を設定する。
- ローカル確認に必要なoriginは必要最小限だけ追加する。
- 秘密鍵、サーバー用秘密情報、利用元無制限キーを使用しない。

### 12.2 取り扱い `[必須B]`

- キーは `config.js` 以外のHTML、CSS、アプリロジックへ重複記載しない。
- localStorage、sessionStorage、Cookie、IndexedDBへ保存しない。
- 画面、エラーメッセージ、Console、独自ログへ出力しない。
- APIキー付きURLをデバッグ出力しない。
- URL生成時以外に不要な複製を作らず、エラーオブジェクトへURL全体を含めて表示しない。

### 12.3 未設定 `[必須B]`

- 未定義、空文字、空白だけ、または `YOUR_GEOAPIFY_API_KEY` 等のプレースホルダーを未設定と判定する。
- 未設定でもヘッダー、操作UI、地図コンテナ、ライセンス表示を描画し、アプリ全体をクラッシュさせない。
- Geoapifyへのタイル、検索、ルート要求を送らない。
- 「`config.example.js` を参考に `config.js` へ公開用の利用元制限付きキーを設定してください」等、キー値を含まない案内を表示する。
- APIを必要とするボタンは無効化する。現在地取得の可否はAPIキーと独立だが、取得後の地図タイルや経路にはキーが必要である旨を示す。

## 13. ローディング、入力検証、エラー処理

### 13.1 ローディングと二重実行 `[必須B]`

- 出発地検索、目的地検索、現在地取得、ルート検索の処理中状態を個別に管理する。
- 処理対象付近に「検索中」「現在地を取得中」「ルートを検索中」等を文字で表示する。
- 対応する領域へ `aria-busy` を設定する。
- 同じ処理の開始ボタンを無効化し、二重要求を送らない。
- クリア等の回復操作は可能な限り利用可能にし、実行時は処理を中断または無効化する。

### 13.2 HTTPと応答検証 `[必須B]`

- `fetch` のrejectはネットワークエラーとして扱う。
- `response.ok` がfalseならHTTPステータス別の内部判定を行い、利用者にはキー、URL、応答本文を含めず「検索サービスからエラーが返されました（HTTP 403）」等を表示する。
- 401／403ではAPIキーの設定または利用元制限を確認する案内、429では利用上限または時間を置いた再試行の案内を付ける。
- JSON解析失敗、必須配列・数値・geometry不足はAPI応答形式不正として扱う。
- API応答本文をHTMLとして描画しない。

### 13.3 エラー一覧 `[必須B]`

| 条件 | 期待動作 |
| --- | --- |
| APIキー未設定 | 12.3の案内を表示し、Geoapifyへ要求を送らず、画面全体を維持する |
| Leaflet読込失敗 | 地図を初期化できない旨を表示し、未捕捉例外を出さない |
| 地図タイル読込失敗 | 地図背景を読み込めない旨を通知し、地点状態や操作可能部分を維持する |
| ネットワークエラー | 対象処理を完了扱いにせず、通信を確認して再試行するよう通知する |
| HTTPエラー | ステータスと回復案内を表示し、APIキーや応答本文は表示しない |
| API応答形式不正 | サービス応答を処理できない旨を表示し、不正データを部分採用しない |
| 検索結果0件 | 検索語を具体化するよう案内し、候補や地点を自動確定しない |
| 同名・曖昧な検索結果 | 補足付き候補一覧を表示し、利用者の選択を待つ |
| 位置情報非対応 | 検索でAを指定する代替手段を案内する |
| 位置情報利用拒否 | 拒否された旨とブラウザ設定または検索利用を案内する |
| 位置情報取得タイムアウト | 10秒以内に取得できなかった旨と再試行を案内する |
| その他の現在地取得失敗 | 取得できない旨を表示し、既存地点を維持する |
| AまたはB未設定 | 不足地点を具体的に表示し、ルートAPIを呼ばない |
| AとBが10m以下 | 実質的に同一である旨を表示し、ルートAPIを呼ばない |
| ルートが見つからない | 地点または移動手段の変更を案内し、無効な旧経路を残さない |
| 古い非同期応答 | 画面、候補、地点、経路、通知のいずれにも採用しない |

### 13.4 失敗時の状態維持 `[必須B]`

- A検索失敗でBを消さず、B検索失敗でAを消さない。
- 新しい候補検索の失敗で、同じ側の確定済み地点も消さない。
- 現在地取得失敗で検索から確定したAやBを消さない。
- ルート検索失敗では今回の条件に対応しない旧経路を表示せず、A、B、現在地、直線距離を維持する。
- 回復可能なエラー後も入力変更、再検索、クリアを実行できる。

## 14. レスポンシブ対応

### 14.1 375px幅 `[必須B]`

- viewport幅375pxでページ全体の横スクロールを発生させない。
- 出発地、目的地、移動手段、各ボタン、地図、結果を自然な縦配置にする。
- 520px以下では検索入力と幅70〜84px程度の「検索」ボタンを横一列にし、入力へ `min-width: 0` を適用して画面外へ押し出さない。320px相当で収まらない場合だけ縦配置へ戻してよい。
- 候補の長い住所、エラー文、確定地点名を折り返し、幅を壊さない。
- 520px以下の地図は約300pxの高さと利用可能な横幅を確保し、指でパン・ズームできるようにする。
- 地図帰属表示は折り返し可能とし、地図外や画面外へはみ出さない。
- 44px程度の押下領域を目安に、主要ボタンと候補を操作しやすくする。
- 520px以下では「経路をクリア」と「地点をすべてクリア」を均等な2列で横一列にし、320px相当で収まらない場合だけ縦配置へ戻してよい。
- 520px以下に限り、本文サイズ、44px以上の操作領域、長文の行間、通知・エラーの視認性を維持しながら、ヘッダー、パネル、カード、結果、領域間の余白を縮小する。

### 14.2 800px以下 `[必須B]`

- 操作領域、地図、結果の順で1列に配置する。
- AとBの検索領域、経路操作を無理に横一列へ詰め込まない。
- 地図は521〜800px幅で約380px、520px以下で約300pxとし、周囲の操作と結果にも過度なスクロールなしで到達できるようにする。
- 地図見出し内の通知、見出し、凡例は利用可能な幅に応じて縦方向へ再配置し、通知文を画面外へ押し出さない。

### 14.3 広い画面 `[必須B]`

- 地点・経路操作と地図を並べ、確定地点や条件と結果を見比べやすくする。
- 操作パネルと地図の上端を揃えてよいが、内容量によって高さを不自然に強制一致させない。
- 結果領域は地図直下または両列の下に、直線距離と経路情報の区別が分かる形で配置する。
- 地図は幅1201px以上で約440px、801〜1200pxで約420pxとする。デスクトップではヘッダー、通知、パネル、地点カードの余白を読みやすさと操作対象の高さを損なわない範囲で抑え、一般的なノートPCで主要操作と結果へ到達しやすくする。
- A/B地点カードは幅にかかわらず左列で縦配置し、デスクトップでは検索入力と検索ボタンを横一列にする。
- 幅1101px以上では地図見出し、全体通知、マーカー凡例を同じ見出し行へ配置する。長い通知は利用可能幅で折り返し、地図本体や凡例へ重ねない。
- 幅1101px以上のヘッダーは、1段目を補助ラベルと横並びのデータ利用バッジ、2段目をアプリタイトルと説明文の横並びとする。1100px以下ではタイトルと説明文を縦配置に戻す。

## 15. アクセシビリティ

### 15.1 キーボード操作 `[必須B]`

- 検索入力、検索実行、候補選択、現在地取得、移動手段、ルート検索、入れ替え、各クリアをキーボードで操作できる。
- 検索入力でEnterを押すと、その入力に対応する検索だけを実行する。
- 候補はTabで移動し、EnterまたはSpaceで選択できる。
- 地図コンテナへフォーカスした際はLeafletの標準キーボード操作でパン・ズームできる。
- DOM順と視覚順を大きく矛盾させず、フォーカスを見えるアウトラインで示す。
- 新しい候補表示後は入力のフォーカスを奪わず、件数を通知し、利用者がTabで候補へ移動できる。

### 15.2 名前と状態 `[必須B]`

- 全入力に `label` を関連付け、プレースホルダーだけをラベルにしない。
- A検索とB検索のボタン名を区別する。
- 候補のアクセシブル名に対象側、主要ラベル、補足を含める。
- A、B、現在地マーカーへ目的が分かる `title` / `alt` 等を設定する。
- ローディングを文字と `aria-busy`、入力エラーを `aria-invalid` と `aria-describedby` で伝える。
- 無効操作は `disabled` 等の標準状態で伝える。

### 15.3 地図以外の情報 `[必須B]`

- 地図や経路線だけを情報の唯一の表現にしない。
- A、B、現在地の有無と名称を文字でも表示する。
- 直線距離、経路距離、所要時間、移動手段を文字で表示する。
- 検索候補を地図マーカーだけでなくHTMLの一覧として提供する。

### 15.4 色への非依存 `[必須B]`

- A、B、現在地を文字または形でも区別する。
- エラー、ローディング、選択、無効状態を色だけで伝えない。
- 経路線が見えなくても、結果領域で経路の有無と数値を確認できる。

## 16. セキュリティ、プライバシー、外部通信

### 16.1 DOM出力 `[必須B]`

- 検索語、候補名、住所、API応答、エラー内容をHTML文字列として実行しない。
- テキスト出力は `textContent` 等の安全なDOM APIを使う。
- URLは固定したHTTPS originとpathへ `URL` / `URLSearchParams` で構築し、API応答由来のURLを実行しない。
- インラインイベント属性を使用しない。

### 16.2 位置情報 `[必須B]`

- 現在地は利用者が明示操作した場合だけ取得する。
- 正確な座標を画面、Console、永続ストレージへ記録しない。
- 地点検索では検索語に加え、近隣候補の順位付けに使用する反対側の確定地点、現在地、または地図中心の座標をGeoapifyへ送信する。
- 利用者が現在地を明示的に取得した後、その現在地が検索biasの優先順位で採用された場合は現在地座標を送信する。現在地がAとして確定しルート検索を行う場合はwaypointとしても送信する。
- 位置情報利用にはGitHub PagesのHTTPS、または開発時のlocalhost等のsecure contextが必要である旨を案内する。

### 16.3 外部通信先 `[必須A][必須B]`

| 送信先 | 用途 | 送信内容 |
| --- | --- | --- |
| `https://maps.geoapify.com/v1/tile/...` | 地図タイル | z/x/y、スタイル、制限付きAPIキー |
| `https://api.geoapify.com/v1/geocode/search` | 住所・施設検索 | 検索語、言語、件数、形式、近隣候補を優先する確定地点・現在地・地図中心のいずれかの座標、制限付きAPIキー |
| `https://api.geoapify.com/v1/routing` | 経路検索 | A/B座標、徒歩または車、形式、制限付きAPIキー |

- 上表以外の分析、広告、ログ収集、Webフォント、CDN等へ通信しない。
- Networkで通信先を確認できるよう、不要な外部リソースを加えない。
- Geoapifyへ送るデータと第三者サービス利用を画面またはプライバシー説明から確認できるようにする。

### 16.4 保存 `[必須B]`

- APIキー、検索語、検索履歴、地点、座標、経路をlocalStorage、sessionStorage、Cookie、IndexedDBへ保存しない。
- Service WorkerやCache APIによる独自のオフライン保存を行わない。
- ブラウザやGeoapifyが通常の通信処理として管理するキャッシュは本アプリの永続化機能とはみなさない。

## 17. ライセンスと帰属表示

### 17.1 Leaflet `[必須B]`

- Leaflet 1.9.4の公式配布ファイルとライセンスをローカル同梱する。
- 画面フッターまたはソースから「Leaflet 1.9.4」と `vendor/leaflet/LICENSE` の所在を確認できるようにする。
- 開発版、mainブランチのスナップショット、別バージョンを混在させない。
- Leaflet既定の帰属接頭辞を非表示にする場合も、フッターでLeaflet 1.9.4の使用とライセンスを明示する。

### 17.2 地図データ・サービス `[必須B]`

- `osm-bright` タイルを使用する地図上に、少なくとも次のリンク付き帰属を常時表示する。
  - `Powered by Geoapify`
  - `© OpenMapTiles`
  - `© OpenStreetMap contributors`
- Geoapifyの契約プランで追加条件がある場合はその条件にも従う。帰属をCSSで隠さない。
- 検索・経路データについても、Geoapify利用をフッターまたは説明で確認できるようにする。

## 18. 対象外 `[MVP外]`

- ユーザー登録、ログイン、権限管理
- サーバー、データベース、独自プロキシ
- 秘密鍵をブラウザから秘匿する仕組み

- 入力中に自動通信するオートコンプリート
- 候補の自動確定
- 地図クリックまたはマーカーのドラッグによる地点指定
- 経由地、3地点以上、複数経路、代替経路選択
- ターンごとのナビゲーション、音声案内、リアルタイム追従
- 公共交通、自転車、トラック等、徒歩・車以外の移動手段
- 渋滞情報、料金、高速道路回避等の詳細条件
- 逆ジオコーディング
- ルートや地図画像の保存、共有、印刷
- オフライン地図、Service Worker、PWA
- Geoapify以外のタイル、検索、経路サービスへの切り替え
- 距離単位の切り替え
- 多言語切り替え

## 19. 実装完了の判定条件

### 19.1 機能 `[必須A]`

- 札幌市中心部の地図を表示し、拡大、縮小、ドラッグ移動できる。
- AとBを明示的な検索と候補選択で個別に確定できる。
- A、B、現在地を色以外でも識別できる。
- 現在地を利用者操作で取得し、Aへ設定できる。
- 現在地とBの直線距離をHaversine式で算出し、経路距離と区別して表示できる。
- 徒歩または車の経路を検索し、線、距離、推定所要時間を表示できる。
- A/B入れ替え、経路クリア、地点全クリアが仕様どおり動作する。

### 19.2 品質 `[必須B]`

- APIキー未設定、タイル失敗、通信・HTTP・応答形式、検索0件、位置情報、地点不足、同一地点、ルートなしを仕様どおり処理する。
- AbortControllerとrequestIdにより古い応答が新しい状態を上書きしない。
- 非同期処理中の状態が文字で分かり、同じ操作を二重実行しない。
- 失敗時に関係のない確定済み地点を消さない。
- 375pxと広い画面で主要操作と結果確認ができ、ページ全体に横スクロールがない。
- キーボードで主要操作を完了でき、地図以外の文字情報でも地点と結果を確認できる。
- APIキーや正確な現在地が画面、Console、Storageへ漏れない。
- アプリ由来の未捕捉例外がConsoleにない。
- 受入チェックリストの全項目を実ブラウザで確認できる。

### 19.3 技術構成 `[必須B]`

- Vanilla HTML/CSS/JavaScriptとローカル同梱したLeaflet 1.9.4で動作する。
- ビルド工程を必要とせず、GitHub Pagesで公開できる。
- Geoapifyの地図タイル、Geocoding API、Routing APIだけを指定用途で使用する。
- LeafletライセンスとGeoapify、OpenMapTiles、OpenStreetMapの帰属を確認できる。
- APIキーは公開用の利用元制限付きキーとして専用設定ファイルに分離される。
- `[MVP外]` のUIや処理を追加していない。

## 20. 解釈を固定した事項

課題文を機能追加で広げず、実装差を防ぐため次のように固定する。

- 「住所または施設名」はGeoapify Forward Geocoding APIの自由入力 `text` で検索し、Autocomplete APIやPlaces APIは使用しない。
- 検索範囲は日本に限定しない。初期表示だけを札幌市中心部とする。
- 候補上限は、選択可能性とAPI・DOM負荷の均衡を取る最小補完として5件とする。
- 複数・同名候補は異常終了ではなく、曖昧である旨を案内して選択を待つ状態とする。
- 「実質的に同一」は、GPSや検索結果の微小差を吸収し、無意味な経路要求を避けるため10m以下とする。
- 現在地と目的地の直線距離は、Aが現在地かどうかにかかわらず `currentLocation` とBから計算する。
- 「経路と地点のクリア」は、地点を残す「経路をクリア」と、現在地を含む全地点を消す「地点をすべてクリア」の2操作で満たす。
- 初回の経路検索は明示ボタン方式とし、一度手動検索した比較セッション中は移動手段変更とA/B入れ替えで自動更新する。候補選択または現在地取得による地点変更後は再び手動検索を必要とする。
- 経路候補はGeoapify応答の最初の有効経路1件に限定し、代替経路UIは追加しない。
- 地図タイルは帰属条件が明確な `osm-bright` に固定する。
- APIキー未設定時はGeoapify通信を停止するが、画面構造と設定案内、APIキーに依存しない基本UIは維持する。
