## 0. 試験条件

- [ ] **0-01：試験用Supabaseプロジェクトを用意する** `[必須B]`
  - 操作：公開用publishable key、RLS、Realtimeを使用できる専用プロジェクトを用意し、秘密鍵をブラウザへ渡さない。
  - 期待結果：本番データへ影響せず、service_role、secret key、DBパスワード、JWT秘密鍵がクライアントに存在しない。

- [ ] **0-02：2利用者・2ブラウザを用意する** `[必須A]`
  - 操作：異なるメールアドレス2件と、通常ウィンドウ＋シークレットウィンドウまたは別ブラウザを用意する。
  - 期待結果：互いに独立したAuthセッションで同じチャットルームを試験できる。

- [ ] **0-03：メール確認あり／なしを試験できる** `[必須A]`
  - 操作：メール確認を有効にした構成と、無効にした試験構成でサインアップする。
  - 期待結果：両構成の分岐を確認でき、設定値と期待結果が試験記録に残る。

- [ ] **0-04：50件超の履歴を用意する** `[必須A]`
  - 操作：権限を守った通常の送信操作等で、少なくとも101件のメッセージを用意する。
  - 期待結果：最新50件、2回以上の過去履歴追加、終端を確認できる。

## B. アカウント作成とメール確認

- [ ] **B-01：メール確認なしの登録** `[必須A]`
  - 操作：利用者1の有効なメールアドレスとパスワードでアカウントを作成する。
  - 期待結果：登録処理は1回だけ実行され、認証済み・プロフィール未設定画面へ進む。

- [ ] **B-02：メール確認ありの登録** `[必須A]`
  - 操作：確認必須の構成で利用者2を登録する。
  - 期待結果：確認待ちが明示され、確認前はチャット・プロフィールDB操作を開始しない。

- [ ] **B-03：メール確認完了** `[必須A]`
  - 操作：localhostとGitHub Pagesで登録し、queryまたはhashを含むPart 4から送信された確認メールの許可済みリンクを開く。
  - 期待結果：queryとhashを除いた送信元環境のPart 4へ戻る。未デプロイの別環境へ転送されず、セッションを安全に処理し、プロフィールがなければプロフィール設定画面を表示する。

- [ ] **B-04：登録入力検証** `[必須B]`
  - 操作：空、不正なメール形式、空またはプロジェクト要件未満のパスワードで送信する。
  - 期待結果：該当入力へ関連付いたエラーを表示し、不正な要求を送らない。

- [ ] **B-05：登録失敗の列挙耐性** `[必須A]`
  - 操作：既存メール、誤入力等で登録に失敗する。
  - 期待結果：アカウントの存在や内部Auth詳細を断定しない共通文言を表示する。

- [ ] **B-06：登録の二重実行防止** `[必須B]`
  - 操作：登録ボタンを素早く複数回操作する。
  - 期待結果：処理中表示となり、同一登録要求を重複送信しない。

## C. ログイン・セッション・ログアウト・再設定

- [ ] **C-01：ログイン成功** `[必須A]`
  - 操作：確認済み利用者の正しい資格情報でログインする。
  - 期待結果：プロフィールの有無を判定し、完成済みならチャット、未設定なら設定画面へ進む。

- [ ] **C-02：ログイン失敗** `[必須A]`
  - 操作：誤ったメールまたはパスワードでログインする。
  - 期待結果：どちらが正しいか、アカウントが存在するかを過度に推測できないエラーとなる。

- [ ] **C-03：ログイン二重実行防止** `[必須B]`
  - 操作：ログイン処理中に送信操作を繰り返す。
  - 期待結果：要求は重複せず、処理中状態が解除されるまで操作が抑止される。

- [ ] **C-04：セッション復元** `[必須A]`
  - 操作：ログイン済みでページを再読み込みする。
  - 期待結果：有効セッションを復元し、同じ利用者のプロフィールとチャットを表示する。

- [ ] **C-05：トークン更新** `[必須B]`
  - 操作：セッションの自動refreshを発生させる。
  - 期待結果：同一利用者の履歴・購読を重複初期化せず利用を継続する。

- [ ] **C-06：セッション失効** `[必須A]`
  - 操作：サーバー側でセッションを失効させ、RESTまたはRealtime操作を行う。
  - 期待結果：購読を解除し、プロフィール・メッセージ・入力を画面とメモリから消して再ログインを案内する。

- [ ] **C-07：ログアウト** `[必須A]`
  - 操作：チャット画面またはプロフィール画面でログアウトする。
  - 期待結果：購読と保護データを破棄し、未ログイン画面へ戻る。再読み込みしてもチャットを表示しない。

- [ ] **C-08：送信中のログアウト** `[必須B]`
  - 操作：送信応答を遅延させ、送信中にログアウトする。
  - 期待結果：後着した旧送信応答が未ログイン画面や次の利用者へ反映されず、自動再送もしない。

- [ ] **C-09：パスワード再設定要求** `[必須B]`
  - 操作：localhostとGitHub Pagesのログイン画面から登録済み・未登録メールそれぞれで再設定を要求し、Networkのredirect URLを確認する。
  - 期待結果：登録有無を断定しない同じ完了案内となる。redirect先は現在のPart 4 URLから既存query・hashを除いた安全な基底URLに、秘密情報を含まない `authFlow=password-recovery` だけを付ける。

- [ ] **C-10：新パスワード設定** `[必須B]`
  - 操作：recoveryリンクを開き、一致する有効な新パスワードを2回入力して保存する。その後、旧パスワードと新パスワードで順にログインし、さらにページを再読み込みする。
  - 期待結果：リンクから必ず再設定画面になり、更新後はsignOutしてログイン画面へ戻り、「パスワードを変更しました。新しいパスワードでログインしてください。」と表示する。旧パスワードは拒否され、新パスワードは成功し、通常ログインや更新後の再読み込みでrecovery画面を誤表示しない。

- [ ] **C-11：recovery認証イベント競合** `[必須B]`
  - 操作：PASSWORD_RECOVERYの前後にSIGNED_IN、INITIAL_SESSION、USER_UPDATEDと遅延したプロフィール取得応答を異なる順序で発生させる。
  - 期待結果：recovery状態中は常に新パスワード画面を優先し、チャット・プロフィール画面へ遷移しない。更新成功とsignOut後だけrecovery状態を解除する。

- [ ] **C-12：無効な再設定リンク** `[必須B]`
  - 操作：使用済み、期限切れ、改変済みの再設定リンクをそれぞれ開き、初期URLと処理後URLを確認する。
  - 期待結果：通常ログインへ黙って戻らず「再設定リンクが無効または期限切れです」と再要求を案内する。Supabaseの認証判定前はcode/hashを保持し、判定後だけ認証情報をURLから除去する。URLやtoken値をConsoleへ出力しない。

## H. 2利用者のRealtime

- [ ] **H-01：相互リアルタイム送受信** `[必須A]`
  - 操作：2ブラウザで別利用者としてログインし、利用者1、利用者2の順に送信する。
  - 期待結果：双方で相手の新着がリロードなしに1件ずつ表示される。

- [ ] **H-02：購読確立後の初期取得** `[必須A][必須B]`
  - 操作：SUBSCRIBED直後から初期履歴応答前の間に別ブラウザから送信する。
  - 期待結果：Realtimeイベントと初期履歴をIDでマージし、取りこぼし・重複がない。

- [ ] **H-03：接続状態表示** `[必須A]`
  - 操作：初期接続、正常接続、通信断、復旧を順に発生させる。
  - 期待結果：「接続中／接続済み／再接続中／切断」をチャットタイトル付近で文言とアイコンにより区別する。初回の正常接続では上部に「チャットに接続しました」を表示せず、切断・再接続・失敗等は上部通知でも案内する。接続完了はaria-liveで通知される。
