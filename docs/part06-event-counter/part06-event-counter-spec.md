## 3. データモデル

### 3-1. イベントオブジェクト [必須B]

```js
{
  id: string,         // 一意識別子（空文字不可）
  name: string,       // イベント名（trim済み、1文字以上）
  date: string,       // 目標日。"YYYY-MM-DD" 形式の暦日
  createdAt: number   // 登録日時（エポックミリ秒）。並び順のタイブレークに使う
}
```

| フィールド | 区分 | 備考 |
|---|---|---|
| `id` | [必須B] B6 | `crypto.randomUUID()` で生成。未対応環境向けに `Date.now().toString(36) + Math.random().toString(36).slice(2)` をフォールバックとする |
| `name` | [必須A] A1 | 6-1のルールで正規化した値 |
| `date` | [必須A] A1 | **文字列のまま保持する。`Date` オブジェクトに変換して保存しない**（5-2） |
| `createdAt` | [必須B] B7 | 登録時に設定し、編集しても変更しない |

**`updatedAt` は持たない。** 並び順にも表示にも使わないため、持っても用途がない。

### 3-2. 日付を文字列で保持する理由 [必須B] B3

`Date` オブジェクトやエポックミリ秒で保存すると、保存時と読み込み時でタイムゾーンが異なった場合に日付が1日ずれる。**目標日は時刻を持たない「暦日」であり、`"2026-09-10"` という文字列そのものが正しい表現である。**

### 3-3. 保存スキーマ [必須B] B9

```js
{
  version: 1,        // 整数
  events: [ /* イベントオブジェクトの配列 */ ]
}
```

- `version` は**整数の `1`**（文字列 `"1"` ではない）
- `events` は配列。0件（空配列）も正常な値

### 3-4. 実行時状態（永続化しない） [必須B]

| 項目 | 内容 |
|---|---|
| `mode` | フォームの状態。`create`（新規登録） / `edit`（編集中） |
| `editingId` | 編集中のイベントの `id`。`create` のときは `null` |
| `today` | 現在日の暦日（5-1で算出した整数） |

## 5. 日数計算仕様

**本章が Part 6 の中核である。**

### 5-1. 暦日への正規化 [必須B] B2/B3

**日数計算は、時刻を含む `Date` の差分ではなく、暦日を表す整数（エポック日）同士の差で行う。**

```
① 目標日の文字列 "YYYY-MM-DD" を、年・月・日の3つの整数に分解する
   ・文字列を Date のコンストラクタや Date.parse に直接渡さない

② 現在日を取得する
   const now = new Date();
   年 = now.getFullYear()  月 = now.getMonth() + 1  日 = now.getDate()
   ・ローカルタイムの「今日」を取得する

③ 双方を Date.UTC で epoch day（1970-01-01 からの日数）に変換する
   epochDay(y, m, d) = Date.UTC(y, m - 1, d) / 86400000

④ 差分を取る
   diff = epochDay(目標日) - epochDay(今日)
```

**③で `Date.UTC` を使う理由 [必須B] B3：** ローカルタイムの深夜同士で引き算をすると、夏時間の切り替え日が23時間または25時間になり、`/ 86400000` が整数にならず1日ずれる。`Date.UTC` は常に1日＝86400000ミリ秒であり、**`diff` は必ず整数になる。**

**①で文字列を `Date` に直接渡してはならない理由 [必須B] B3：** `new Date("2026-09-10")` は ISO 日付形式として **UTC の深夜**に解釈される。UTC−5 の地域では現地時間 `2026-09-09 19:00` となり、`getDate()` が `9` を返して**1日前になる**。日本（UTC+9）では表面化しないため、開発中に気づきにくい。

**禁止事項 [必須B]：**

| # | 禁止する実装 |
|---|---|
| NG1 | `new Date(dateString)` / `Date.parse(dateString)` で `"YYYY-MM-DD"` を解釈する |
| NG2 | `(targetDate - todayDate) / 86400000` をローカルタイムの `Date` 同士で計算する |
| NG3 | `Math.ceil` / `Math.floor` で端数を丸めて日数を出す（③④なら端数が発生しない） |
| NG4 | `getTimezoneOffset()` で補正する（夏時間の切り替え日で誤る） |

### 5-2. 「あと何日」の定義 [必須B] B1

| 状況 | `diff` | 定義 |
|---|---|---|
| 目標日が今日 | `0` | **今日を 0 とする** |
| 目標日が明日 | `1` | **明日を 1 とする** |
| 目標日が3日後 | `3` | |
| 目標日が昨日 | `-1` | |

**起点は「今日 = 0」。** 明日は1、昨日は −1 となる。

### 5-3. 現在日の判定基準 [必須B]

**利用者の端末のローカルタイムを基準とする。** サーバ時刻・UTC は用いない（外部API不使用の方針、および利用者の体感と一致させるため）。

### 5-4. 表示文言 [必須A] A2 / [必須B] B1

| `diff` | 表示 |
|---|---|
| `diff > 0` | `あと◯日`（例：`あと12日`） |
| `diff === 0` | **`今日`** |
| `diff < 0` | **`◯日前`**（例：`3日前`。`-3` の絶対値を用いる） |

**`diff === 0` を「あと0日」ではなく「今日」とする理由 [必須B]：** 当日であることが最も伝わる表現であり、「あと0日」は解釈が割れる（当日なのか、過ぎたのか）。

**過去のイベントを一覧から自動削除しない [必須B]。** 課題文に削除条件の記載がなく、利用者の同意なくデータを消してはならない。過去のイベントは経過日数を表示したまま一覧に残す（8-2）。

### 5-5. 目標日の表示形式 [必須B]

`2026年9月16日` 形式で表示する（月・日はゼロ埋めしない）。

- 曜日は表示しない（[MVP外]）
- HTMLでは `<time datetime="2026-09-16">2026年9月16日</time>` とする [必須B]。機械可読な値を保持するため

### 5-6. 計算例（受入テストの基準）

現在日を `2026-09-04` としたときの期待値。

| 目標日 | `diff` | 表示 |
|---|---|---|
| `2026-09-04` | `0` | `今日` |
| `2026-09-05` | `1` | `あと1日` |
| `2026-09-16` | `12` | `あと12日` |
| `2026-09-03` | `-1` | `1日前` |
| `2026-09-01` | `-3` | `3日前` |
| `2027-09-04` | `365` | `あと365日` |
| `2026-03-01` | `-187` | `187日前` |

**うるう年の確認 [必須B]：** `2028-02-29` は実在する日付として登録・計算できること。`2028-03-01` と `2028-02-28` の差が2日であること。

## 6. 入力・エラー仕様

### 6-1. イベント名 [必須A] A1 / [必須B] B4

| # | 仕様 |
|---|---|
| N1 | `<input type="text">` を用いる |
| N2 | **前後の空白（半角・全角）を除去してから検証・保存する** |
| N3 | **除去後に空文字となる入力は登録できない**（空欄・空白のみの入力を禁止する） |
| N4 | **最大50文字**（除去後の文字数）。超過時は登録できない |
| N5 | 文字列中（間）の空白は除去しない |
| N6 | 使用できる文字に制限を設けない（記号・絵文字・改行以外の任意の文字を許可する） |
| N7 | 入力欄には `maxlength` 属性を設定してよいが、**JavaScript側の検証を省略してはならない**（保存データ由来の値も検証するため） |

**N4の50文字は確定値である**（13章 U3）。

### 6-2. 目標日 [必須A] A1 / [必須B] B5

| # | 仕様 |
|---|---|
| D1 | **`<input type="date">` を用いる** |
| D2 | **過去の日付も登録できる**（13章 U10） |
| D3 | 未入力（`value` が空文字）の場合は登録できない |
| D4 | 値の形式は `"YYYY-MM-DD"` |
| D5 | 保存データから読み込んだ日付は、6-3の検証を通す |

**`<input type="date">` を用いる理由 [必須B]：** Part 5 では不正入力を検出できないため `type="number"` を避けたが、`type="date"` は事情が異なる。**`value` は「空文字」か「妥当な `YYYY-MM-DD`」のいずれかしか返さない**ため、`abc` や `2026-02-30` のような値が入力欄から入ってくることがない。検証は「未入力かどうか」だけで足り、スマートフォンではネイティブの日付ピッカーが使える。

**日付の入力可能範囲に制限を設けない [必須B]。** `min` / `max` 属性を指定しない（過去日も遠い未来も登録できる）。

### 6-3. 日付文字列の検証 [必須B]

**保存データから読み込んだ `date` は、入力欄を経由していないため、次の2段階で検証する。**

```
① 形式の検証
   /^\d{4}-\d{2}-\d{2}$/ に完全一致すること

② 実在する日付かの検証
   年・月・日に分解し、Date.UTC(y, m-1, d) から
   getUTCFullYear / getUTCMonth+1 / getUTCDate を取り出して
   元の3つの整数と一致すること

   ・"2026-02-30" は Date.UTC が 3月2日に繰り上げるため不一致となり、不正と判定される
```

### 6-4. エラーメッセージ [必須A] / [必須B]

**メッセージは1度に1つだけ表示する。** 複数該当する場合は下表の上から優先する。

| # | 条件 | メッセージ |
|---|---|---|
| M1 | イベント名が空（前後空白除去後） | `イベント名を入力してください` |
| M2 | イベント名が50文字を超える | `イベント名は50文字以内で入力してください` |
| M3 | 目標日が未入力 | `目標日を選択してください` |

**[必須B] 表示上の要件：**

| # | 仕様 |
|---|---|
| MS1 | メッセージ領域は、メッセージが無いときも高さを確保し、表示のたびにレイアウトが上下に動かないこと |
| MS2 | 色だけでエラーを表現しない（文言を必ず表示する） |
| MS3 | メッセージ領域に `role="alert"` を付与する |
| MS4 | エラーのある入力欄に `aria-invalid="true"` を設定する |
| MS5 | 登録／保存に成功したら、メッセージは即座に消える |

### 6-5. 検証のタイミング [必須B]

## 8. 一覧・並び順仕様

### 8-1. 一覧の構造 [必須A] A5 / [必須B]

| # | 仕様 |
|---|---|
| L1 | 一覧は `<ul>` / `<li>` で構成する |
| L2 | 見出しに登録件数を表示する（例：`登録したイベント（3件）`） |
| L3 | 0件のときは空状態メッセージを表示する（4-4） |
| L4 | 件数の上限を設けない |

### 8-2. 並び順 [必須B] B7

**一覧を概念的に2グループに分け、グループ間の順序を固定する。**

```
グループ1：未来・当日（diff >= 0）  ← 目標日の昇順（近い順）
──────────────────────────────
グループ2：過去（diff < 0）        ← 目標日の降順（最近過ぎたものが先）
```

| # | 仕様 |
|---|---|
| S1 | 未来・当日のイベントを上に、過去のイベントを下に置く |
| S2 | 未来・当日グループは**目標日の昇順**（今日 → 明日 → …）。「あと何日」が少ない順になる |
| S3 | 過去グループは**目標日の降順**（昨日 → 一昨日 → …）。「◯日前」が少ない順になる |
| S4 | グループ間に区切りを入れるかは実装者の裁量とする（必須ではない） |

**S3で過去グループを降順にする理由 [必須B]：** 全体を単純な日付昇順にすると、最も古い過去のイベントが一覧の先頭に来てしまう。過去は「直近に過ぎたもの」ほど関心が高いため、降順とする。

### 8-3. タイブレーク [必須B] B7

**目標日が同一の場合、`createdAt` の昇順（先に登録したものが上）とする。`createdAt` も同一の場合は `id` の昇順とする。**

これが無いと、同じ日のイベントの順序が実行のたびに変わり、受入テストで判定できない。

| # | 契機 |
|---|---|
| R1 | 起動時（localStorage からの読み込み後） |
| R2 | 登録後 |
| R3 | 編集の保存後 |
| R4 | 削除後 |
| R5 | 現在日が変わったことを検知したとき（10章） |

**並び順の切替UIは実装しない**（[MVP外]）。

## 9. localStorage 仕様

### 9-1. 保存 [必須A] A6 / [必須B] B9

| 項目 | 仕様 |
|---|---|
| キー | **`part06-event-counter.events`** |
| 値 | 3-3のスキーマを `JSON.stringify` した文字列 |
| 保存単位 | 全イベントを1キーにまとめて保存する |
| 保存タイミング | 登録・編集の保存・削除の直後（それぞれ即座に） |

### 9-2. 読み込み [必須B] B9

ページ読み込み時に1回実行する。

| # | 仕様 |
|---|---|
| LD1 | localStorage へのアクセスと `JSON.parse` を `try / catch` で囲む |
| LD2 | キーが存在しない場合、0件の状態で正常に起動する（初回起動時） |
| LD3 | **ルート構造が不正な場合**（JSONとして解析できない／オブジェクトでない／`version` が `1` でない／`events` が配列でない）、**0件の状態で起動し、通知領域に警告を表示する** |
| LD4 | **`events` の個々の要素が不正な場合、その要素だけをスキップし、残りを読み込む。** スキップが1件でも発生したら通知領域に警告を表示する |
| LD5 | 白画面・エラーで停止しない |

### 9-3. 要素の検証 [必須B]

`events` の各要素について、以下をすべて満たすものだけを読み込む。

| # | 項目 | 条件 |
|---|---|---|
| V1 | 要素そのもの | オブジェクトであること（`null`・配列は不可） |
| V2 | `id` | `string` 型で、空文字でないこと |
| V3 | `name` | `string` 型で、**前後空白の除去後に1文字以上50文字以内**であること |
| V4 | `date` | `string` 型で、**6-3の①②を満たすこと** |
| V5 | `createdAt` | `number` 型で、有限値であること |

**不足項目の補完・型変換は行わない。** 条件を満たさない要素はスキップする。

### 9-4. 読み込み時と登録時で扱いを分ける理由 [必須B]

| | 検証失敗時の動作 |
|---|---|
| 入力フォーム | エラーメッセージを出し、登録しない（6-4） |
| localStorage 読み込み | 不正な要素だけをスキップし、残りを読み込む（LD4） |

**LD4で「全体を破棄」としない理由：** 本アプリにはエクスポート機能が無く（[MVP外]）、保存データが唯一のデータである。1件の破損で全イベントを失わせるべきではない。

### 9-5. 通知メッセージ [必須B]

| # | 条件 | メッセージ |
|---|---|---|
| T1 | ルート構造が不正（LD3） | `保存データを読み込めませんでした` |
| T2 | 一部の要素をスキップ（LD4） | `一部の保存データを読み込めませんでした` |
| T3 | 保存に失敗（9-6） | `保存できませんでした` |

通知領域（4-2 ⑤）に表示する。`role="alert"` を付与し、非表示時も高さを確保する。

### 9-6. 保存失敗 [必須B]

| # | 仕様 |
|---|---|
| SV1 | 書き込みを `try / catch` で囲む |
| SV2 | 失敗した場合、T3の通知を表示する |
| SV3 | **保存失敗を黙って無視しない**（コンソールエラーのみで済ませない） |
| SV4 | 失敗してもアプリは動作を継続する（画面上のデータは保持される） |
| SV5 | 通知は、次の保存が成功するまで残す |

**SV2の理由：** 保存されたと思って画面を閉じるとデータを失うため。プライベートモードや容量超過で発生し得る。

### 10-1. 再計算の契機 [必須B] B12

### D. タイムゾーン・日付ズレ（5-1）

**開発者ツールの Sensors パネル等でタイムゾーンを変更して確認する。**

**このテストの目的：** 「タイムゾーンを変えても同じ表示になること」を確認するのではない。**5-3の通り、現在日は利用者端末のローカルタイムを基準とする**ため、タイムゾーンによって「今日」が異なる暦日を指すのは正しい挙動である。

例：日本が `2026-09-04` でも、Los Angeles ではまだ `2026-09-03` の場合がある。このとき目標日 `2026-09-04` の正しい表示は、日本では `今日`、Los Angeles では `あと1日` である。**両者が一致しないことが正常である。**

確認すべきは次の2点。

1. **各タイムゾーンにおける端末ローカルの現在日を基準として、暦日差が正しく計算されること**
2. **UTC解釈や夏時間（DST）による意図しない1日ズレが発生しないこと**

### 13-1. タイムゾーンに関する補足

**5-3の通り、現在日は利用者端末のローカルタイムを基準とする。** したがって、同じイベントでもタイムゾーンによって表示が1日分異なることがあり、**それは仕様通りの正しい挙動である**（日本で `今日` のイベントが、Los Angeles ではまだ `あと1日` であり得る）。

## 付録：実装者へ渡す際の注意事項

1. **出力ファイルは `apps/part06-event-counter/` 配下の `index.html` / `style.css` / `app.js` の3つのみ**
2. **フレームワーク・外部ライブラリ・CDN・外部API・Webフォントを使わない**
3. **本仕様書2-2の[MVP外]機能を追加しない。** 思いついても実装せず、提案にとどめる
4. **日数計算は `Date.UTC(y, m-1, d) / 86400000` による epoch day の差で行う。** `new Date("YYYY-MM-DD")` / `Date.parse` を使わない（UTC解釈で1日ずれる）
5. **ローカルタイムの `Date` 同士の引き算をしない**（夏時間で23時間・25時間になる）
6. **`Math.ceil` / `Math.floor` で日数を丸めない**（epoch day 方式なら端数が出ない）
7. **今日=0、明日=1。`diff === 0` は `今日`、`diff < 0` は `◯日前`**
8. **目標日は `"YYYY-MM-DD"` 文字列のまま保存する。** `Date` やタイムスタンプに変換しない
9. **目標日の入力は `<input type="date">`。** `min` / `max` を設定しない（過去日も登録可）
10. **イベント名は前後空白を除去し、空文字と50文字超を拒否する**
11. **検証は登録／保存ボタンを押した時点で行う**（入力のたびのリアルタイム検証はしない）
12. **エラー時はフォームの入力内容を保持する**（消さない）
13. **イベント名の描画は `textContent`。`innerHTML` に連結しない**
14. **localStorage のキーは `part06-event-counter.events`。** 値は `{ version: 1, events: [...] }`
15. **読み込み時、ルート構造が不正なら0件で起動＋警告。個々の要素が不正ならその要素だけスキップ＋警告**（全体を破棄しない）
16. **保存失敗を黙殺しない**（通知を出す）
17. **並び順は「未来・当日を昇順」→「過去を降順」。** 同日は `createdAt` 昇順、さらに `id` 昇順でタイブレーク
18. **登録・編集保存・削除のたびに並び順を再適用し、即座に保存する**
19. **編集中に対象を削除したら `create` モードへ戻す。対象以外なら編集モードを維持する**
20. **編集・削除ボタンにイベント名を含む `aria-label` を付ける**
21. **一覧に `aria-live` を付けない**（再描画のたびに全体が読み上げられる）
22. **`visibilitychange` で現在日を再取得し、変わっていたときだけ再描画する。** `setInterval` を使わない
23. **`outline: none` を単独で指定しない**
24. **入力欄のフォントサイズは16px以上**（iOSの自動ズーム防止）
25. **幅375pxで崩れないこと。長いイベント名が折り返すこと**
