## 3. Canvas仕様

### 3-1. 採用 [必須A] A1

**`<canvas>` を1つ用い、2Dコンテキストで描画する。**

| # | 理由 |
|---|---|
| 1 | 自由描画に適している |
| 2 | マウス・タッチ双方の座標を同じ方式で扱える |
| 3 | PNG等への保存が容易（`toBlob`） |

**描画内容をDOM要素の集合（`<div>` や SVG要素の羅列）で表現する方式を採用しない [必須A]。**

### 3-2. 描画コンテキストの初期設定 [必須A] A1 / [必須B]

| 設定 | 値 | 理由 |
|---|---|---|
| `lineCap` | **`"round"`** | 線の端が四角にならない |
| `lineJoin` | **`"round"`** | 折れ目が滑らかになる |
| `globalCompositeOperation` | **`"source-over"`**（ペン時） | 通常の重ね描き（8章） |

| # | 仕様 |
|---|---|
| C1 | `lineCap` / `lineJoin` は初期化時に1回設定する |
| C2 | **`canvas.width` / `height` へ代入するとコンテキストの設定が初期化される。** 代入する場合は設定をやり直す（本仕様では初期化時のみ代入する。6章） |

### 3-3. 線の連続性 [必須B]

**pointerが速く動いても、点の列ではなく連続した線に見えること。**

| # | 仕様 |
|---|---|
| C3 | `pointermove` のたびに、**前回座標から現在座標へ線を引く**（`moveTo` → `lineTo` → `stroke`） |
| C4 | 現在座標を「前回座標」として保存し、次回に使う |
| C5 | 点だけを描く実装（`fillRect` や `arc` を座標ごとに置く）にしない |

**C5の理由 [必須B]：** `pointermove` は連続的に発火するとは限らず、速く動かすと座標が大きく飛ぶ。**点を置くだけでは、飛んだ区間が途切れて破線になる。**

## 4. Pointer Events仕様

### 4-1. 採用 [必須A] A7 / [必須B] B1

**Pointer Events を用いる。マウスイベントとタッチイベントを二重に実装しない。**

| 観点 | **Pointer Events（採用）** | `mouse*` ＋ `touch*` の二重実装 |
|---|---|---|
| 対応する入力 | マウス・タッチ・ペンを**同じ処理で扱える** | それぞれ別に実装が必要 |
| コード量 | 1系統 | 2系統（分岐と重複が生じる） |
| 挙動の一貫性 | 同一 | **マウスとタッチで挙動が食い違いやすい** |
| 座標の取得 | `clientX` / `clientY`（共通） | タッチは `touches[0].clientX` と形が異なる |
| 二重発火 | 起きない | **タッチ時に `mouse*` も発火し、二重に描かれることがある** |
| 対応ブラウザ | 最新の Chrome / Safari で対応済み | — |

**二重実装を避ける最大の理由 [必須B] B1：** タッチ操作では、`touchstart` の後に互換の `mousedown` が発火する。**両方を購読すると1回のタッチで2回描画処理が走る。** `preventDefault` による抑止が必要になり、実装が複雑化する。

### 4-2. 使用するイベント [必須A] A7

| イベント | 処理 |
|---|---|
| `pointerdown` | 描画開始 |
| `pointermove` | 描画継続 |
| `pointerup` | 描画終了 |
| `pointercancel` | 描画終了 |

**`pointercancel` を必ず購読する [必須B]。** システムのジェスチャ割り込みや、ブラウザによるポインタの取り消しで発火する。**購読しないと `isDrawing` が `true` のまま残り、次に触れた瞬間に意図しない線が引かれる。**

### 4-3. 状態遷移 [必須B]

```
待機（isDrawing = false）
  ↓ pointerdown
描画中（isDrawing = true, activePointerId = e.pointerId）
  ↓ pointermove（activePointerId と一致するもののみ）
描画中（前回座標から現在座標へ線を引く）
  ↓ pointerup / pointercancel（activePointerId と一致するもののみ）
待機（isDrawing = false, activePointerId = null）
```

### 4-4. pointerdown [必須A] A1

| # | 仕様 |
|---|---|
| P1 | `isDrawing = true` にする |
| P2 | **`activePointerId` に `e.pointerId` を保存する**（4-6） |
| P3 | **`canvas.setPointerCapture(e.pointerId)` を呼ぶ**（4-5） |
| P4 | 現在座標を「前回座標」として記録する |
| P5 | **その場に点を1つ描く**（クリック／タップだけでも点が残るようにする） |

**P5の理由 [必須A] A1：** `pointerdown` → `pointerup` のみで `pointermove` が発生しない場合、線が1本も引かれない。**タップしても何も描かれないのは、お絵描きツールとして不自然である。**

#### P5の実装方式 [必須B]

**第一候補：同一点への `moveTo` → `lineTo` → `stroke`**

```js
ctx.beginPath();
ctx.moveTo(x, y);
ctx.lineTo(x, y);
ctx.stroke();
```

`lineCap = "round"` により、円形の点が描かれる。

| # | 仕様 |
|---|---|
| P5a | **この方式で点が描画されることを、実ブラウザで必ず確認する**（19章 B-5・B-6） |
| P5b | **描画されない環境・実装があった場合、クリック／タップ時のみ円形の点を描く方式へ切り替える** |

**切り替え時の実装（第二候補）：**

```js
ctx.beginPath();
ctx.arc(x, y, ctx.lineWidth / 2, 0, Math.PI * 2);
ctx.fill();
```

| # | 仕様 |
|---|---|
| P5c | **切り替えるのは `pointerdown` 時の点の描画のみ**。`pointermove` による線の描画方式（3-3 C3）は変更しない |
| P5d | 第二候補を採る場合、**消しゴム時も同じ合成モード（`destination-out`）が適用されること**（`fill` も合成モードの影響を受ける） |
| P5e | 第二候補を採る場合、**塗り色（`fillStyle`）を現在の色に合わせること**（`strokeStyle` だけ設定して `fillStyle` が黒のまま、という誤りを避ける） |
| P5f | どちらの方式を採ったかを、実装後に依頼者へ報告する |

**同一点への `lineTo` が描画されない可能性について [必須B]：** 仕様上は `lineCap = "round"` で点が描かれるが、**ブラウザの実装や、パスの扱い方によっては描画されないことがある。** 実機で確認したうえで方式を確定する。

**P5cが重要である [必須B]：** 点の描画方式を変えても、**線の描画は「前回座標から現在座標へ `lineTo`」のまま維持する。** 両方を `arc` にすると、速く動かしたときに点の列になる（3-3 C5）。

### 4-5. setPointerCapture [必須B]

**`setPointerCapture()` を用いる。**

| # | 理由 |
|---|---|
| 1 | **Canvas外へドラッグしても `pointerup` を確実に受け取れる** |
| 2 | 受け取れないと `isDrawing` が `true` のまま残り、Canvasへ戻った瞬間に意図しない線が引かれる |
| 3 | ブラウザ標準の機能であり、追加の実装が不要 |

| # | 仕様 |
|---|---|
| P6 | `pointerdown` で `setPointerCapture(e.pointerId)` を呼ぶ |
| P7 | `pointerup` / `pointercancel` で `releasePointerCapture(e.pointerId)` を呼ぶ（ブラウザが自動解放する場合もあるが、明示的に行う） |
| P8 | 解放時に例外が発生し得るため、`try / catch` で囲むか、`hasPointerCapture()` で確認してから呼ぶ |

### 4-6. 複数ポインタの扱い [必須B] B9

**描画対象は常に1本のポインタのみとする。**

| # | 仕様 |
|---|---|
| P9 | `pointerdown` 時、**すでに `isDrawing === true` なら、その `pointerdown` を無視する** |
| P10 | `pointermove` / `pointerup` / `pointercancel` は、**`e.pointerId === activePointerId` のときのみ処理する** |
| P11 | 一致しないポインタからのイベントは何もしない |
| P12 | マルチタッチによる同時描画を実装しない（[MVP外]。2-2 の19） |

**P9・P10の理由 [必須B] B9：** 2本指でCanvasに触れると、2つ目のポインタからも `pointermove` が発火する。**判定しないと、2本目の指の軌跡が1本目のストロークに接続され、画面を横切る意図しない直線が引かれる。**

### 4-7. Canvas外へ出た場合 [必須B]

| # | 仕様 |
|---|---|
| P13 | **座標をclampしない。** Canvasのクリップに任せる |
| P14 | Canvas外の区間は描画されない |
| P15 | Canvas内へ戻ったら、そのまま描画が続く |
| P16 | `pointerup` は確実に受け取り、`isDrawing = false` にする（4-5） |

**clampしない理由 [必須B]：** clampすると、Canvas外へ出ている間もCanvasの縁に沿って線が引かれ続ける。**「枠に沿って太い線が描かれる」という不自然な結果になる。** クリップに任せれば、外に出た区間は描かれず、戻った位置から自然に続く。

### 4-8. 描画中の設定変更 [必須B]

| # | 仕様 |
|---|---|
| P17 | 色・線幅・ツールの変更は、**次のストロークから反映される** |
| P18 | 描画中のストロークの途中で設定を切り替える処理を実装しない |

**理由 [必須B]：** UIを操作するにはポインタがCanvasから離れるため、実質的にストローク終了後の変更となる。**途中で切り替える複雑な処理は不要である。**

## 5. 描画座標仕様

### 5-1. 座標変換 [必須B] B2 ← 必ず守る

**`clientX` / `clientY` をそのままCanvas座標として使わない。**

```js
function toCanvasPoint(event, canvas, dpr) {
  const rect = canvas.getBoundingClientRect();
  const scaleX = canvas.width / rect.width;    // 内部px ÷ CSS px
  const scaleY = canvas.height / rect.height;
  return {
    x: (event.clientX - rect.left) * scaleX / dpr,
    y: (event.clientY - rect.top) * scaleY / dpr
  };
}
```

| # | 仕様 |
|---|---|
| X1 | **`getBoundingClientRect()` で Canvas の位置と CSS表示サイズを取得する** |
| X2 | **`canvas.width / rect.width` で内部解像度への倍率を掛ける** |
| X3 | `ctx.setTransform(dpr, 0, 0, dpr, 0, 0)` を適用している場合、**さらに `dpr` で割る**（6-2） |
| X4 | `getBoundingClientRect()` は**イベントのたびに呼ぶ**（スクロールやレイアウト変更で位置が変わるため） |

### 5-2. 誤りやすい実装 [必須B] B2

**検証結果（375px幅、Canvas表示321px、内部1400px、dpr=2、`rect.left = 15` の場合）：**

| 実装 | `clientX = 200` のときの結果 | 正誤 |
|---|---|---|
| `clientX` をそのまま使う | **200** | **誤り**（Canvasの位置を考慮していない） |
| `clientX - rect.left` のみ | **185.00** | **誤り**（内部解像度の倍率が抜けている。正しい値の約 1/2.18） |
| **X1〜X3 の方式** | **403.43** | **正しい** |

**「rect で位置は補正したが、内部解像度の倍率を忘れる」誤りが最も起きやすい [必須B]。** 見た目では「少しずれる」程度に見えるが、**表示サイズが小さいほどずれが大きくなる。**

### 5-3. 座標変換の検証結果 [必須B]

**純関数として実装し、以下のケースで検証した。不一致0件。**

| ケース | 入力 | 期待座標 | 結果 |
|---|---|---|---|
| PC・dpr=1・等倍（表示700／内部700） | 中央 | (350, 262.5) | **一致** |
| PC・dpr=2（表示700／内部1400） | 中央 | (350, 262.5) | **一致** |
| **375px・dpr=2（表示321×240.75／内部1400）** | 左上 | (0, 0) | **一致** |
| 375px・dpr=2 | 中央 | (350, 262.5) | **一致** |
| 375px・dpr=2 | 右下 | (700, 525) | **一致** |
| ページスクロール中（`rect.top = -50`） | — | 補正される | **一致** |

**表示サイズが 321px でも 700px でも、Canvas座標系（700×525）上の同じ位置を指す [必須B]。** これにより、画面幅が変わっても「指した位置に線が出る」。

## 6. リサイズ／高DPI対応

### 6-1. 内部解像度の決定 [必須B] B3 ← 本Partの要点1

**内部解像度は初期化時に1回だけ決め、以後変更しない。**

```js
const MAX_CSS_WIDTH = 700;          // PCでの最大表示幅
const ASPECT = 3 / 4;               // 高さ ÷ 幅（4:3）
const dpr = Math.min(window.devicePixelRatio || 1, 3);

canvas.width  = Math.round(MAX_CSS_WIDTH * dpr);
canvas.height = Math.round(MAX_CSS_WIDTH * ASPECT * dpr);
ctx.setTransform(dpr, 0, 0, dpr, 0, 0);
```

| # | 仕様 |
|---|---|
| R1 | **内部解像度は「最大表示幅 × dpr」で決める**（現在の表示幅ではない） |
| R2 | **`devicePixelRatio` の上限を 3 とする**（6-3） |
| R3 | **初期化後、`canvas.width` / `canvas.height` へ二度と代入しない**（6-4） |
| R4 | CSS側で表示サイズを指定する（`width: 100%`、`max-width: 700px`、`aspect-ratio: 4 / 3`） |
| R5 | 描画座標は常に「CSS基準の座標系（700×525）」で扱う |

### 6-2. `setTransform` の役割 [必須B]

`ctx.setTransform(dpr, 0, 0, dpr, 0, 0)` を適用することで、**以降の描画は 700×525 の座標系で行える。**

| # | 仕様 |
|---|---|
| R6 | **線幅も同じ座標系（Canvas論理座標）で指定する。** `lineWidth = 5` は**論理座標上の5**であり、CSSピクセルの5pxとは限らない（9-4） |
| R7 | 座標変換（5-1）でも `dpr` で割り、同じ座標系に揃える |

**R6の注意 [必須B]：** Canvas の論理座標は 700×525 に固定され、**表示サイズはCSSで変わる**（6-4 案C）。そのため、**表示幅が700pxより小さい環境では、線も同じ比率で縮小して表示される。** 詳細と実測値は9-4に示す。

### 6-3. `devicePixelRatio` の上限 [必須B] B3

**上限を 3 とする。**

**検証結果（最大表示幅700px、4:3）：**

| `devicePixelRatio` | 採用dpr | 内部解像度 | メモリ | 700px表示時に必要な実効px | 判定 |
|---|---|---|---|---|---|
| 1 | 1 | 700×525 | 1.4MB | 700 | **鮮明** |
| 2 | 2 | 1400×1050 | 5.6MB | 1400 | **鮮明** |
| 3 | 3 | 2100×1575 | **12.6MB** | 2100 | **鮮明** |

**上限を2にした場合、dpr=3 の環境で700px表示すると内部1400px に対し実効2100px が必要となり、ぼやける。** 上限3であれば全環境で鮮明さを保てる。

### 6-4. リサイズ時に描画内容を失わない方式 [必須B] B4 ← 本Partの要点2

**`canvas.width` / `canvas.height` へ代入すると、Canvasの内容は完全に消える。** これは仕様上の挙動であり、回避できない。

#### 方式の比較

| 方式 | 内容 | 実装量 | 内容の保持 | 採否 |
|---|---|---|---|---|
| A | リサイズ時に一時Canvasへ退避し、サイズ変更後に復元する | 中 | 保持できるが、**拡大縮小で画質が劣化する** | 不採用 |
| B | 描画ストローク履歴を保持し、リサイズ時に再描画する | **大** | 保持できる | **不採用** |
| **C** | **内部解像度を初期化後に変更しない。表示サイズのみCSSで変える** | **最小** | **原理的に失われない** | **採用** |

#### 案Cを採用する理由 [必須B] B4

| # | 理由 |
|---|---|
| 1 | **`canvas.width` へ代入しないため、内容が消えることが原理的に起こらない** |
| 2 | **退避・復元の処理が不要**。リサイズ時に何もしなくてよい |
| 3 | 座標変換（5-1）が `getBoundingClientRect()` を毎回参照するため、**表示サイズが変わっても座標がずれない** |
| 4 | 内部解像度を「最大表示幅 × dpr」で確保しているため、**表示が拡大されてもぼやけない**（6-3） |
| 5 | 案Bはストローク履歴の保持が必要になり、**Undo（[MVP外]）と同等の実装量**になる |

**案Bを不採用とする理由 [必須B]：** 25章の通り、本仕様ではストローク履歴を保持しない。**履歴を導入すると、課題の範囲を大きく超える。**

#### 案Cで実際に起きること [必須B]

| 操作 | 結果 |
|---|---|
| ウィンドウ幅を変える | **絵はそのまま。表示サイズだけが変わる**（絵も一緒に拡大縮小して表示される） |
| スマートフォンを回転する | **絵はそのまま。表示サイズだけが変わる** |
| リサイズ後に描く | **指した位置に正しく線が出る**（5-1により座標が追従する） |

**「絵が消える」ことも「座標がずれる」ことも起こらない [必須B]。**

#### リサイズ時に実装すること [必須B]

| # | 仕様 |
|---|---|
| R8 | **`resize` イベントで Canvas に対して何もしなくてよい** |
| R9 | 座標変換で毎回 `getBoundingClientRect()` を呼ぶため、追加処理は不要（5-1 X4） |

## 8. 消しゴム仕様

### 8-1. 実装方式 [必須A] A4 / [必須B] B5 ← 本Partの要点3

|---|---|---|
| **`destination-out`（採用）** | 既存ピクセルを透明にする | **採用** |

#### 白で描く方式を採用しない理由 [必須B] B5

| # | 理由 |
|---|---|
| 1 | **背景色が白以外になると破綻する**（白い線が残って見える） |

| 3 | **本当に消しているわけではない**。上に塗り重ねているだけであり、ツールの意味と実装が食い違う |
| 4 | 白を色として選べる場合（7-1 L3で除外）、消しゴムと区別できなくなる |

### 8-2. 合成モードの切替 [必須B] B5

| ツール | `globalCompositeOperation` |
|---|---|
| ペン | **`"source-over"`** |
| 消しゴム | **`"destination-out"`** |

| # | 仕様 |
|---|---|
| E1 | **ツールを切り替えるたびに設定する** |
| E2 | **ペンへ戻したとき、必ず `"source-over"` へ戻す** |
| E3 | 描画の直前（`pointerdown` 時）に、現在のツールに応じて設定する方式でもよい |
| E4 | 保存処理・全消去処理の前後で、合成モードが変わったまま残らないこと |

**E2を守らないと何が起きるか [必須B]：** 消しゴムから色を選んでペンに戻したつもりでも、`destination-out` のままだと**線を引くほど絵が消えていく。** 見た目は「透明な線で消している」状態になり、原因が分かりにくい。

| 独立した固定幅 | 不採用 | 消しゴム専用のUIが必要になる |
| ペンの一定倍率 | 不採用 | 倍率の根拠がなく、利用者が太さを予測しにくい |

**課題要件（A4「一部を消せる」）は、この方式で十分満たせる [必須B]。**

### 8-4. ペン／消しゴムの切替UI [必須A] A4 / [必須B]

|---|---|

### 8-5. 色ボタンを押したときの挙動 [必須B]

| **確認なしで即時クリア（採用）** | **採用** | 課題自体が簡易ツールであり、描き直しの頻度が高い |
| `confirm()` で確認 | 不採用 | ブラウザ依存のUIで操作感を損ねる。頻繁に描き直す用途では煩わしい |

**副作用を認めたうえでの判断である [必須B]：** Undo（[MVP外]）がないため、**誤操作で消した絵は戻せない。** これを補うため、次の配置上の対策を必須とする。

| # | 対策 |
|---|---|
| N5 | **「すべて消す」ボタンを、保存ボタンから十分に離して配置する** |
| N6 | **危険な操作として視覚的に区別する**（枠線・文字色などで他のボタンと差を付ける） |
| N7 | ただし、色だけで区別しない（文言で「すべて消す」と明示する） |

（22章 U7）

### 10-3. 設定の扱い [必須B]

**全消去はCanvasの内容だけを消す。色・線幅・ツールは初期値に戻さない。**

| 対象 | 全消去時 |
|---|---|
| Canvasの内容 | **消す** |
| 色 | **維持する** |
| 線幅 | **維持する** |
| ツール（ペン／消しゴム） | **維持する** |

**理由 [必須B]：** 利用者が設定した色や線幅まで勝手に戻す必要はない。**「同じ設定で描き直す」が最も多い使い方である。**

## 11. PNG保存仕様

### 11-1. 形式と方法 [必須A] A6

**PNG形式で保存する。`toBlob()` ＋ `<a download>` を用いる。**

| # | 仕様 |
|---|---|
| S1 | `canvas.toBlob(callback, "image/png")` を用いる |
| S2 | `URL.createObjectURL(blob)` でURLを作る |
| S3 | `<a>` に `href` と `download` を設定してクリックする |
| S4 | **使用後に `URL.revokeObjectURL()` を呼ぶ** |

#### `toDataURL()` ではなく `toBlob()` を用いる理由 [必須B]

| # | 理由 |
|---|---|
| 1 | **大きな画像をData URL文字列としてメモリに保持しなくてよい** |
| 2 | Blob URL を使えるため、URLの長さ制限を受けない |
| 3 | **`revokeObjectURL()` で明示的に解放できる** |

**PNGを選ぶ理由 [必須A] A6：** 線や透明部分を劣化なく保存できる。JPEGは非可逆圧縮で線がにじみ、お絵描き用途に適さない。

### 11-2. ファイル名 [必須B]

**`drawing-YYYYMMDD-HHmmss.png` 形式とする。**

**検証結果：**

| 日時 | ファイル名 | 不正文字 |
|---|---|---|
| 2026-09-06 18:30:00 | `drawing-20260906-183000.png` | **なし** |
| 2026-01-02 03:04:05 | `drawing-20260102-030405.png` | **なし** |
| 2026-12-31 23:59:59 | `drawing-20261231-235959.png` | **なし** |

| # | 仕様 |
|---|---|
| S5 | 日時はローカルタイムを用いる |
| S6 | 月・日・時・分・秒は**2桁にゼロ埋めする** |
| S7 | **`/` `:` `*` `?` `"` `<` `>` `|` `\` を含めない** |
| S8 | 利用者がファイル名を指定するUIは実装しない（[MVP外]） |
| S9 | **精度は秒までとする。ミリ秒・連番を付けない** |

**日時を付ける理由 [必須B]：** 固定名（`drawing.png`）だと、保存するたびに `drawing (1).png` のように連番が付くか、上書き確認が出る。**日時を付けることで、通常の使い方では重複しにくくなる。**

#### 同一秒内に連続保存した場合 [必須B] ← 重複は仕様として許容する

**精度が秒までであるため、同じ秒のうちに2回保存すると、ファイル名は同一になる。**

**実測：**

| 保存時刻 | ファイル名 | 前回と同名か |
|---|---|---|
| 18:30:00.100 | `drawing-20260906-183000.png` | — |
| 18:30:00.900 | `drawing-20260906-183000.png` | **同名** |
| 18:30:01.000 | `drawing-20260906-183001.png` | 異なる |

| # | 仕様 |
|---|---|
| S10 | **同一秒内の連続保存でファイル名が重複することを、仕様として許容する** |
| S11 | **重複を避けるための連番付与・ミリ秒付与・保存済みファイル名の記録を実装しない** |
| S12 | 同名になった場合の扱いは**ブラウザに委ねる**（連番を付ける、上書き確認を出す等、ブラウザにより異なる） |
| S13 | **同一秒内であっても、保存処理そのものは成功すること**（エラーにしない） |

**重複回避を実装しない理由 [必須B]：**

| # | 理由 |
|---|---|
| 1 | 連番を付けるには**保存済みファイル名を記録する必要がある**が、ブラウザは実際に保存されたかを通知しない。**記録と実態が食い違う** |
| 2 | ミリ秒を付けるとファイル名が読みにくくなる（`drawing-20260906-183000123.png`） |
| 3 | **同一秒内に2回保存する操作は例外的**であり、その場合もブラウザ側で連番が付く |
| 4 | Part 11・14 と同じ方針で、**確率的・例外的な事象のために処理を追加しない** |

**受入テストでも「ファイル名が必ず異なること」を条件にしない**（19章 J-9）。

（22章 U10）

### 11-3. 保存時の背景 [必須A] A6 / [必須B] B6 ← 本Partの要点4

**画面上は白背景に見せ、保存時も白背景のPNGとする。**

| 方式 | 保存結果 | 採否 |
|---|---|---|
| A. 透明背景のまま保存 | 消した箇所と描いていない箇所が透明 | **不採用** |
| **B. 保存時だけ白背景を合成（採用）** | **白背景のPNG** | **採用** |
| C. Canvas自体を常に白で塗る | 白背景だが、`destination-out` で消すと**白まで消えて透明になる** | **不採用** |

#### 案Bを採用する理由 [必須B] B6

| # | 理由 |
|---|---|
| 1 | **一般的なお絵描きツールとして分かりやすい** |
| 2 | **消しゴムで消した箇所も、保存画像では白になる**（周囲と同じ見た目になる） |
| 3 | **透明PNGと知らず、別アプリで黒背景に表示される事故を防げる** |

#### 案Cを採用しない理由 [必須B]

**Canvas自体を白で塗ると、`destination-out` の消しゴムが白ごと消してしまう。** 消した箇所は透明になり、画面上で背景（CSSの背景色）が透けて見える。**結局、白背景を保っていることにならない。**

#### 実装方式 [必須B] B6

```
① 一時Canvasを作る（表示中Canvasと同じ内部解像度）
② 一時Canvasを白で塗りつぶす
③ 一時Canvasに、表示中Canvasを drawImage で重ねる
④ 一時Canvasから toBlob でPNGを取り出す
```

| # | 仕様 |
|---|---|
| S9 | **一時Canvasは `document.createElement("canvas")` で作り、DOMへ追加しない** |
| S10 | 一時Canvasの `width` / `height` は、**表示中Canvasの内部解像度と同じ**にする |
| S11 | `drawImage` は等倍で行う（拡大縮小しない） |
| S12 | 保存後、一時Canvasへの参照を残さない（ガベージコレクションに任せる） |

### 11-4. 保存処理でCanvasを変更しない [必須B] B7 ← 必ず守る

**保存処理によって、表示中のCanvasの絵が変化してはならない。**

| # | 仕様 |
|---|---|
| S13 | **表示中のCanvasへ白を塗らない** |
| S14 | 表示中のCanvasの `globalCompositeOperation` を保存処理で変更しない |
| S15 | 白背景の合成は**一時Canvas上でのみ**行う（11-3） |
| S16 | 保存の前後で、表示中のCanvasのピクセルが一致すること |

**S13を守らないと何が起きるか [必須B]：** 表示中Canvasに白を塗ると、**保存後に消しゴムが効かなくなる**（白ピクセルを消すと透明になり、下の絵が消える）。また、**保存するたびに絵が白で覆われる。**

### 11-5. 保存失敗時 [必須B]

| # | 仕様 |
|---|---|
| S17 | **`toBlob()` のコールバック引数が `null` の場合**、エラーメッセージを表示する |
| S18 | メッセージは **`画像を保存できませんでした`** |
| S19 | 保存処理全体を `try / catch` で囲み、例外時も同じメッセージを表示する |
| S20 | **過剰な例外分類を行わない**（原因別のメッセージを用意しない） |
| S21 | エラー時もアプリは動作を継続する。Canvasの内容は変化しない |

### 12-2. 描画内容の「正」 [必須B] B10 ← Part 14 との違い

**描画内容については、Canvas自体を正とする。**

| Part | 対象 | 「正」とするもの | 理由 |
|---|---|---|---|
| Part 14 | 迷路 | **迷路データ**（Canvasは描画するだけ） | **迷路データから何度でも再描画できる**。Canvasは表示手段に過ぎない |

| # | 仕様 |
|---|---|
| M5 | **描画ストロークの履歴を保持しない**（2-2 の28） |
| M6 | 現在のCanvasのピクセルを描画状態として扱う |
| M7 | **UI状態（M2）と描画内容（M6）で、正とするものが異なることを混同しない** |

**この整理が必要な理由 [必須B] B10：** Part 14 では「Canvasを状態の正にしない」と定めたが、**本Partで同じ方針を採ると、ストローク履歴の保持が必要になる。** それは Undo（[MVP外]）と同等の実装量であり、課題の範囲を超える。

**この方針を採れるのは、6-4（案C）により Canvas の内容が失われないことが保証されているためである [必須B]。** 内部解像度を変更しない限り、Canvasのピクセルは消えない。

## 13. タッチ操作とスクロール

### 13-1. `touch-action` [必須A] A7/A8 / [必須B] B8

**Canvas に `touch-action: none` を指定する。**

|---|---|
| T4 | `touch-action: none` により、`preventDefault()` は原則不要 |
| T5 | 必要な場合も、**Canvas上のイベントに限定する**（ページ全体で抑止しない） |

### 22-1. 線幅の定義に関する修正（U13）

当初案では、6-2 R6 に **「`lineWidth = 5` が CSS基準の 5px 相当になる」** と記載していた。

**この記述は正確ではなかった。**

Canvasの論理座標は 700×525 に固定され、**表示サイズはCSSで変わる**（6-4 案C）。そのため、`lineWidth = 5` の見え方は表示幅に依存する。

**実測：**

| 画面幅 | 表示幅 | 縮小率 | 論理5 の見え方 |
|---|---|---|---|
| 375 | **321** | **0.459** | **約 2.29 CSSピクセル** |
| 768以上 | 700 | 1.000 | **5.00 CSSピクセル** |

（表示幅は6-5の実測値。当初は343pxとしていたが、22-3で321pxへ修正した）

#### 確定内容

| # | 内容 |
|---|---|
| 1 | **線幅は Canvas論理座標上の太さとして扱う** |
| 2 | **画面幅ごとに補正する処理を追加しない**（9-4 W11） |
| 3 | **Canvas全体の縮小に伴い、見た目の線幅も比例して縮小される**（仕様通りの挙動とする） |
| 4 | **UI表記は `5` とし、`5px` としない**（CSSピクセル値と誤認させない。9-2 W2） |
| 5 | range は **1〜30、初期値5** を維持する |
| 6 | **ペンと消しゴムは同じ線幅定義を使う**（9-3 W9） |
| 7 | **375px実機での使い分けやすさは、実使用確認（P-4b）で判定する** |
| 8 | **NGの場合は range の範囲を仕様側から見直す。** 補正処理の追加で対処しない |

**補正しない理由は9-4に3点記載した。** 特に、**保存されるPNGは常に論理座標基準であるため、補正すると保存結果が画面幅に依存してしまう**点が決め手である。

### 22-2. クリック／タップ時の点描画（P5）

**第一候補は、同一点への `moveTo` → `lineTo` → `stroke`（`lineCap = "round"` により円形の点になる）。**

**ただし、この方式で点が描画されることは仕様上保証されているものの、ブラウザの実装やパスの扱い方によっては描画されないことがある。**

| # | 確定内容 |
|---|---|
| 1 | **実ブラウザで必ず確認する**（19章 B-5・B-6） |
| 2 | 描画されない場合、**クリック／タップ時のみ `arc` ＋ `fill` による円形の点を描く方式へ切り替える**（P5b） |
| 3 | **切り替えるのは `pointerdown` 時の点のみ。`pointermove` による線の描画方式は変更しない**（P5c） |
| 4 | 切り替える場合、**消しゴムの合成モードと `fillStyle` の設定に注意する**（P5d・P5e） |
| 5 | **どちらの方式を採ったかを、実装後に依頼者へ報告する**（P5f） |

**3が重要である。** 両方を `arc` にすると、速く動かしたときに点の列になり、3-3 C5 に反する。

### 22-3. 実機確認後の仕様書修正（実装後）

**実装とブラウザ実機確認を経て、仕様書の記述2か所が実装と食い違っていたため修正した。実装は変更していない。**

#### 1. 375px時のCanvas表示幅（6-5・U4）

| | 修正前 | **修正後（実測）** |
|---|---|---|
| 375px時の表示幅 | 343px | **321px** |

**原因：** 修正前の値は「画面幅 − ページ左右余白（32px）」だけを引いた概算だった。**実際にはパネルのpadding（計28px）と枠線（計2px）も引かれる。**

**波及箇所：** 5-2（誤りやすい実装の例）、5-3（座標変換の検証ケース）、6-3（高DPIの十分性）、6-5（サイズ表）、9-4（線幅の見え方）、19章 G-10、22章 U4。
