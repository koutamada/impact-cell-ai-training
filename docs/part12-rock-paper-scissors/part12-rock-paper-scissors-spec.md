## 3. 手の内部表現

### 3-1. 内部値と表示名の分離 [必須B] B1

| 内部値 | 表示名 |
|---|---|
| `rock` | **グー** |
| `scissors` | **チョキ** |
| `paper` | **パー** |

| # | 仕様 |
|---|---|
| H1 | **判定・集計・履歴の記録には、すべて内部値（`rock` / `scissors` / `paper`）を用いる** |
| H2 | **表示名は、表示する直前に内部値から変換する** |
| H3 | 変換は1箇所の対応表で行う（例：`const HAND_LABELS = { rock: 'グー', scissors: 'チョキ', paper: 'パー' }`） |
| H4 | **表示文字列（`グー` 等）を条件分岐や比較に使わない** |
| H5 | ボタンの `data-hand` 属性等で内部値を保持してよい |

**分離する理由 [必須B] B1：** 表示文字列で判定すると、**表示を変えた瞬間に判定が壊れる。** また、全角・半角や表記ゆれが比較の失敗として現れ、原因が分かりにくい。

### 3-2. 順序の固定 [必須B]

**配列やボタンの並び順は `rock` → `scissors` → `paper`（グー → チョキ → パー）で固定する。**

乱数の対応（4-1）とボタンの表示順を同じ順序に揃えることで、対応表が1つで済む。

### 3-3. 絵文字を使わない [必須B]

**手や勝敗を絵文字（✊✌️✋ など）で表現しない。**

| # | 理由 |
|---|---|
| 1 | 環境により字形が大きく異なり、グーとパーの区別がつきにくい場合がある |
| 2 | スクリーンリーダーでの読み上げが安定しない |
| 3 | 課題文の要件ではない |

**装飾として併記することも実装しない**（表示名のみとする。18章 U5）。

## 4. ランダム生成仕様

### 4-1. 生成式 [必須A] A2 / [必須B] B2

```js
const HANDS = ['rock', 'scissors', 'paper'];
const index = Math.floor(randomValue * 3);
const computerHand = HANDS[index];
```

| 乱数値 | `index` | 手 |
|---|---|---|
| `0` 以上 `0.3333333333333333` 未満 | 0 | **rock（グー）** |
| `0.3333333333333333` 以上 `0.6666666666666666` 未満 | 1 | **scissors（チョキ）** |
| `0.6666666666666666` 以上 `1` 未満 | 2 | **paper（パー）** |

| # | 仕様 |
|---|---|
| R1 | `Math.floor(Math.random() * 3)` を用いる |
| R2 | **3種類が等確率で選ばれる** |
| R3 | `HANDS` 配列の範囲外を参照しない（`undefined` を返さない） |
| R4 | **`Math.round` を使わない**（両端の確率が他の半分になる） |

**`Math.round(Math.random() * 2)` の誤り [必須B]：** 一見3種類が出るが、**`index` が 0 と 2 になる確率が 1 の半分**になる。受入テストで検出する（15章 B-9）。

### 4-2. 決定的にテストできる構造 [必須B] B2 ← 重要

**乱数値を引数として受け取る関数に、手の決定処理を分離する。**

```js
// 乱数値から手を決める（テスト可能）
function handFromRandom(randomValue) {
  return HANDS[Math.floor(randomValue * 3)];
}

// 実際の対戦で呼ぶ
function pickComputerHand() {
  return handFromRandom(Math.random());
}
```

| # | 仕様 |
|---|---|
| R5 | **`Math.random()` の呼び出しと、値から手への変換を分離する** |
| R6 | 変換関数は、任意の乱数値を渡して結果を確認できること |
| R7 | **大量試行による分布確認だけで合否を判定しない**（対応の誤りを見逃すため） |

**この分離が必要な理由 [必須B] B2：** `Math.random()` を関数内で直接呼ぶと、**「0 のとき rock になるか」を確認できない。** 分布だけを見ると、対応表が `['paper','rock','scissors']` のように入れ替わっていても3種類が均等に出るため、**誤りを検出できない。**

### 4-3. 境界値の実測結果 [必須B]

**受入テストの期待値として用いる。** 浮動小数点の都合により、直感と異なる箇所がある。

| 乱数値 | `randomValue * 3` | `index` | 手 |
|---|---|---|---|
| `0` | `0` | 0 | **rock** |
| `0.33333333333333326` | `0.9999999999999998` | 0 | **rock**（境界の直前） |
| **`1/3`（`0.3333333333333333`）** | **`1`** | **1** | **scissors** |
| `0.34` | `1.02` | 1 | scissors |
| `0.6666666666666665` | `1.9999999999999998` | 1 | **scissors**（境界の直前） |
| **`2/3`（`0.6666666666666666`）** | **`2`** | **2** | **paper** |
| `0.67` | `2.01` | 2 | paper |
| `0.9999999999999999`（1未満の最大値） | `2.9999999999999996` | 2 | **paper** |

**`1/3` は `rock` ではなく `scissors` になる [必須B]。** `1/3 * 3` は浮動小数点演算の結果ちょうど `1` になるためである。**「約0.333 なら rock」と誤って期待値を書かないこと。**

**`Math.random()` は `0` 以上 `1` 未満を返すため、`index` が 3 になることはない [必須B]。**

## 5. 勝敗判定仕様

### 5-1. 全9パターン [必須A] A3

**ユーザー視点の結果を示す。**

| ユーザー | コンピュータ | 結果 |
|---|---|---|
| rock | rock | **draw（引き分け）** |
| rock | scissors | **win（勝ち）** |
| rock | paper | **lose（負け）** |
| scissors | rock | **lose（負け）** |
| scissors | scissors | **draw（引き分け）** |
| scissors | paper | **win（勝ち）** |
| paper | rock | **win（勝ち）** |
| paper | scissors | **lose（負け）** |
| paper | paper | **draw（引き分け）** |

**結果の内部値は `win` / `lose` / `draw` とする [必須B]。** 表示文言（6-2）と分離する。

### 5-2. 実装方式 [必須B] B3

**「何に勝つか」の対応表を用いる方式を推奨する。**

```js
const BEATS = {
  rock: 'scissors',   // グーはチョキに勝つ
  scissors: 'paper',  // チョキはパーに勝つ
  paper: 'rock'       // パーはグーに勝つ
};

function judge(userHand, computerHand) {
  if (userHand === computerHand) return 'draw';
  if (BEATS[userHand] === computerHand) return 'win';
  return 'lose';
}
```

| # | 仕様 |
|---|---|
| J1 | **9通りの条件分岐を並べる方式でもよいが、上記の対応表方式を推奨する** |
| J2 | 判定は**ユーザー視点**で行う（`win` はユーザーの勝ち） |
| J3 | 判定関数は、2つの手を受け取り結果を返す**純粋な関数**とする（集計や表示を行わない） |

**対応表方式を推奨する理由 [必須B] B3：**

| # | 理由 |
|---|---|
| 1 | **3行の定義で9パターンすべてを網羅でき、書き漏れ・書き間違いが起こりにくい** |
| 2 | 9通りの分岐は、1行でも `win` と `lose` を取り違えると気づきにくい |
| 3 | 対応表は「グーはチョキに勝つ」という日常の理解とそのまま対応し、レビューで検証しやすい |

**J3の理由：** 判定関数が純粋であれば、9パターンすべてを個別に検証できる（15章 C）。

## 6. 1対戦の処理順・結果表示

### 6-1. 処理順 [必須B] B4

**ボタンが押されたとき、以下の順に処理する。**

```
① ユーザーの手を確定する（押されたボタンの内部値）
② コンピュータの手をランダムに決定する（4章）
③ 勝敗を判定する（5章）
④ 集計値を更新する（7章）
⑤ 履歴に1件追加する（9章）
⑥ 画面を更新する（今回の結果・集計値・勝率・履歴）
```

| # | 仕様 |
|---|---|
| P1 | **①〜⑥を1つの関数にまとめ、ボタンのクリックごとに1回だけ実行する** |
| P2 | **④と⑤は必ず両方実行する。** 一方だけ更新される経路を作らない |
| P3 | ⑥の画面更新は、④⑤で更新した状態から**まとめて描画する** |
| P4 | 非同期処理（`setTimeout`・アニメーション待ち）を挟まない |

**P2の理由 [必須B] B6：** 集計値と履歴が別々に更新されると、**「履歴は11件なのに総対戦数は10」といった食い違い**が生じる。同一関数内で必ず両方を更新する。

**P3の理由：** ④⑤の途中で描画すると、一時的に矛盾した数値が表示され得る。

### 6-2. 今回の結果表示 [必須A] A4

**両者の手と勝敗が一目で分かるように表示する。**

| 項目 | 表示例 |
|---|---|
| ユーザーの手 | `あなた：グー` |
| コンピュータの手 | `コンピュータ：チョキ` |
| 結果 | `結果：勝ち！` |

**結果の文言 [必須A] A4：**

| 内部値 | 表示文言 |
|---|---|
| `win` | **`勝ち！`** |
| `lose` | **`負け`** |
| `draw` | **`引き分け`** |

| # | 仕様 |
|---|---|
| P5 | 文言は意味が一通りに定まるものとする。「あなたの勝ち」など明示的でもよいが、**「○」「×」のような記号のみにしない** |
| P6 | **色だけで勝敗を表現しない**（17章 AC8） |
| P7 | 絵文字を使わない（3-3） |
| P8 | 未対戦時は「まだ対戦していません」等の案内を表示する（空欄で放置しない） |

### 6-3. 結果の通知 [必須B] B10

**今回の結果の表示領域に `aria-live="polite"` を付与する。**

| # | 仕様 |
|---|---|
| P9 | **両者の手と勝敗を1つのまとまりとして読み上げられるようにする**（例：`あなた：グー、コンピュータ：チョキ、結果：勝ち！`） |
| P10 | **集計値・勝率・履歴の領域には `aria-live` を付けない**（17章 AC5・AC6） |

**P10の理由 [必須B] B10：** 1回の対戦で、集計4項目＋勝率＋履歴1件が同時に更新される。**すべてに `aria-live` を付けると、1クリックで7項目以上が読み上げられ、ゲームとして使えなくなる。** 必要な情報は今回の結果に含まれており、集計値は利用者が能動的に読みに行ける。

### 6-5. 手のビジュアルの実装方式 [必須B]

**インラインSVGの `<symbol>` 定義を `<use>` で参照する方式とする。**

| # | 仕様 |
|---|---|
| G1 | **3種類の手（`rock` / `scissors` / `paper`）と、未対戦用の1種類を `<symbol>` として定義する** |
| G2 | 定義はHTML先頭にまとめ、**ゲームロジックと混在させない** |
| G3 | 表示側は `<use href="#hand-rock">` のように参照し、**内部値から `href` を組み立てる**（表示名を使わない。3-1 H4） |
| G4 | **外部画像URL・外部ライブラリに依存しない** |
| G5 | **絵文字を用いない**（3-3）。OS・ブラウザによる字形差を避けるため |
| G6 | **装飾目的のSVGには `aria-hidden="true"` を付け、読み上げの対象にしない**（6-6） |
| G7 | 履歴の小アイコンも同じ `<symbol>` を再利用する（9-2） |

**`<symbol>` ＋ `<use>` を採用する理由 [必須B]：** 3種類の手を1箇所で定義し、結果表示と履歴の両方から再利用できる。**手のデザインを変更する場合も、定義1箇所の修正で済む。**

### 6-6. 視覚表現と支援技術の関係 [必須B] ← 重要

**視覚表現と読み上げ内容を重複させない。**

| 対象 | 扱い |
|---|---|
| 視覚表現（手のイラスト・名前・勝敗の大きな文字） | **`aria-hidden="true"`** とし、読み上げ対象から外す |
| `aria-live="polite"` の要素 | **視覚的には隠す**（`visually-hidden`）が、DOMには残す |
| 読み上げ内容 | **`あなた：パー、コンピュータ：グー、結果：勝ち！`**（6-3 P9のまま変更しない） |

| # | 仕様 |
|---|---|
| V5 | **読み上げ用の要素はDOMから削除しない。** `display: none` にもしない（読み上げられなくなる） |
| V6 | `visually-hidden` は、画面外へ退避させる方式とする（`clip-path` 等） |
| V7 | この構成により、**支援技術では従来どおり1文で結果が伝わり、視覚的には手のビジュアルで伝わる** |

**この方式にする理由 [必須B]：** 視覚表現をそのまま読み上げ対象にすると、`あなたの手 パー 勝ち！ コンピュータの手 グー` のように分断されて読まれる。**6-3 P9 の「1つのまとまりとして読み上げる」を維持するため、読み上げ用の1文を別に持つ。**

**視覚的に隠した要素も、スクリーンリーダーの通常の読み進めで到達できる [必須B]。** 対戦直後の通知だけでなく、後から読み返すこともできる。

| # | 仕様 |

| S6 | 集計値を画面の表示から読み戻して再計算しない（状態を唯一の正とする） |

## 8. 勝率仕様

### 8-1. 定義 [必須A] A6 / [必須B] B5

```
勝率（%） = 勝ち数 ÷ 総対戦数 × 100
```

| # | 仕様 |
|---|---|
| W1 | **引き分けも総対戦数に含める**（分母から除外しない） |
| W2 | **未対戦時（`total === 0`）は 0% とする**（ゼロ除算を発生させない） |

| 例 | 総 | 勝 | 負 | 分 | 勝率 |
|---|---|---|---|---|---|
| 未対戦 | 0 | 0 | 0 | 0 | **0.0%** |
| 1勝 | 1 | 1 | 0 | 0 | **100.0%** |
| 2勝1敗1分 | 4 | 2 | 1 | 1 | **50.0%** |
| 2勝1敗 | 3 | 2 | 1 | 0 | **66.7%** |
| 1勝2敗 | 3 | 1 | 2 | 0 | **33.3%** |

### 8-2. 小数の桁数と丸め [必須B] B5

**小数第1位まで表示する。丸めには `toFixed(1)` を用いる。**

```js
const rate = total === 0 ? 0 : (wins / total) * 100;
const display = rate.toFixed(1) + '%';
```

| # | 仕様 |
|---|---|
| W3 | **常に小数1桁で表示する**（`100%` ではなく **`100.0%`**、`50%` ではなく **`50.0%`**） |
| W4 | 丸めは `toFixed(1)` による |
| W5 | 表示を組み立てる際、`Math.round` などで独自に丸め直さない |

**常に1桁とする理由 [必須B] B5：** 桁数が変動すると、対戦のたびに表示幅が変わって数値が横に揺れる。**`tabular-nums`（7-3 S10）と組み合わせ、表示位置を安定させる。**

### 8-3. 丸めの実測結果 [必須B]

**受入テストの期待値として用いる。**

| 勝 / 総 | 計算値 | 表示 |
|---|---|---|
| 0 / 0 | （0とする） | `0.0%` |
| 1 / 1 | 100 | `100.0%` |
| 2 / 4 | 50 | `50.0%` |
| 2 / 3 | 66.66666666666666 | **`66.7%`** |
| 1 / 3 | 33.33333333333333 | **`33.3%`** |
| 5 / 6 | 83.33333333333334 | `83.3%` |
| 1 / 7 | 14.285714285714285 | `14.3%` |
| 3 / 7 | 42.857142857142854 | `42.9%` |
| 1 / 8 | 12.5 | `12.5%` |
| 1 / 16 | 6.25 | **`6.3%`** |

**`toFixed` は浮動小数点の内部表現に依存するため、`.5` ちょうどの丸め方向を仕様として保証しない [必須B]。** 受入テストでは上表の値を期待値とする。

## 9. 履歴仕様

### 9-1. 「過去の対戦結果」の範囲 [必須A] A5 / [必須B] B7

**各対戦の履歴一覧をMVPに含める。**

課題文は「過去の対戦**結果を記録**し、勝率**など**を確認できる」としており、**集計値だけでは「過去の対戦結果を記録」を素直に満たさない**と解釈する。

**1件あたり、以下を記録する。**

```js
{
  index: number,   // 対戦番号（1始まり）
  userHand: string,   // ユーザーの手（内部値）
  cpuHand: string,    // コンピュータの手（内部値）
```

| # | 仕様 |
|---|---|
| Y1 | **1対戦につき、ちょうど1件を追加する** |
| Y2 | 対戦番号は 1 から始まり、**その対戦時点の `total` と一致する** |
| Y3 | 手は**内部値**で保持し、表示時に表示名へ変換する（3-1 H2） |
| Y4 | 記録した履歴を後から書き換えない |

### 9-2. 表示形式 [必須A] A5

| 表示例 |
|---|
| `3回目：あなた グー / CPU チョキ / 勝ち` |

**4項目を別々の要素に分けて配置してよい [必須B]。** 1本の文字列である必要はない。

| 表示例（要素を分けた場合） |
|---|
| `4回目` ｜（手の小アイコン）｜ `あなた パー / CPU グー` ｜ `勝ち` |

| # | 仕様 |
|---|---|
| Y5 | 対戦番号・ユーザーの手・コンピュータの手・勝敗の4項目を含める |
| Y5b | **手の小アイコンを添えてよい**（6-5 G7 の `<symbol>` を再利用する）。**`aria-hidden="true"` とし、読み上げを重複させない** |
| Y5c | **勝敗をバッジ状に表示してよい。** ただし**文字を必ず含める**（色・形だけにしない） |

| Y7 | `textContent` で設定する |
| Y8 | 色だけで勝敗を表現しない |

### 9-3. 表示順 [必須B] B8

**最新の対戦を上に表示する（新しい順）。**

**理由 [必須B]：** 直前の結果をすぐ確認できる。古い順だと、対戦を重ねるほど最新結果が下へ流れ、スクロールが必要になる。

### 9-4. マークアップ [必須B]

**`<ul>` / `<li>` を用い、対戦番号はテキストに含める。**

| # | 仕様 |
|---|---|
| Y9 | `<ul>` / `<li>` で構成する |
| Y10 | **`<ol>` の自動採番に頼らない。** 対戦番号は `3回目：` のようにテキストへ含める |

**`<ol>` を使わない理由 [必須B]：** 表示順が新しい順（9-3）であるため、`<ol>` の自動採番は 1, 2, 3… と上から振られ、**対戦番号と一致しない。** `reversed` 属性で対応できるが、件数の増加に応じた管理が必要で誤りやすい。**番号を明示的にテキストへ含める方が確実である。**

### 9-5. 表示件数 [必須B] B8

**全件を表示する。ただし履歴領域に最大高さを設け、その内部で縦スクロールさせる。**

| # | 仕様 |
|---|---|
| Y11 | **集計値・履歴とも全件を保持する** |
| Y12 | **表示も全件とする**（最新N件のみに絞らない） |
| Y13 | 履歴領域に `max-height` を設定し、`overflow-y: auto` で内部スクロールさせる |
| Y14 | 履歴が0件のときは「まだ対戦していません」等の案内を表示する |
| Y15 | **ページネーション・履歴削除UI・フィルタを実装しない**（[MVP外]） |

**全件表示を採用する理由 [必須B] B8：**

| # | 理由 |
|---|---|
| 1 | 課題文の「過去の対戦結果を記録」を素直に満たす。**最新10件のみだと、11件目以降の記録が確認できなくなる** |
| 2 | 「画面が極端に長くなる」懸念は、**表示件数を減らさなくても、CSSの `max-height` ＋ 内部スクロールで解決できる** |
| 3 | 1件1行のテキストであり、100件でもDOM要素は100個程度。**性能上の問題にならない** |
| 4 | 表示件数の制限は、**集計値（全件）と表示（10件）が食い違う状態**を生み、利用者を混乱させる |

**`max-height` の指定は、ページネーション（[MVP外]）ではなく単なるスタイル指定である [必須B]。** 表示件数を制限するものではない。

**`max-height` と `overflow-y: auto` の設定は必須である [必須B]。** これがないと、対戦を重ねるほどページが縦に長くなり、集計値やボタンが画面外へ押し出される。

（18章 U6）

## 10. 連打・二重処理

### 10-1. 方針 [必須B] B9

**1クリック＝1対戦として処理する。ロック・待機処理を追加しない。**

| # | 仕様 |
|---|---|
| L1 | 処理はすべて同期的に完結する（6-1 P4） |
| L2 | **連打防止のためのフラグ・`disabled` 制御・デバウンスを実装しない** |
| L3 | **アニメーション待ち・遅延演出を実装しない**（[MVP外]） |

**ロックを追加しない理由 [必須B] B9：** 処理が同期的であれば、クリックイベントは順番に処理され、**1クリックごとに確実に1対戦が成立する。** ロックを入れると、かえって「連打すると一部のクリックが無視される」という挙動になり、ゲームとして不自然である。

### 10-2. 二重集計を防ぐ実装上の注意 [必須B] B9

| # | 注意点 |
|---|---|
| L4 | **イベントリスナを重複して登録しない**（同じボタンに複数回 `addEventListener` しない） |
| L5 | 3つのボタンに個別に登録する場合も、**登録は初期化時の1回のみ**とする |
| L6 | 集計の更新は6-1の関数の中だけで行い、**他の場所から呼ばない** |
| L7 | ボタンを `<form>` の中に置かない（`submit` との二重発火を避ける） |

**L4の理由：** リスナが2回登録されると、1クリックで2回集計され、`total` が2ずつ増える。**受入テストで、10回クリックして `total` が10になることを確認する**（15章 F-2）。

### 18-1. 乱数の境界値に関する確定（U3関連）

**`Math.floor(Math.random() * 3)` の境界値を実測し、受入テストの期待値として確定した**（4-3）。

| 乱数値 | 手 |
|---|---|
| `0` | rock |
| `0.33333333333333326` | rock（境界の直前） |
| **`1/3`（`0.3333333333333333`）** | **scissors** |
| `0.6666666666666665` | scissors（境界の直前） |
| **`2/3`（`0.6666666666666666`）** | **paper** |
| `0.9999999999999999` | paper |

**`1/3` は `rock` ではなく `scissors` になる。** `1/3 * 3` が浮動小数点演算の結果ちょうど `1` になるためである。**「約0.333 なら rock」と誤った期待値を書かないこと**（受入項目 B-3）。

### 18-2. 結果通知の設計に関する確定

**今回の結果の領域にのみ `aria-live="polite"` を付け、集計値・勝率・履歴には付けない**（6-3・13章 AC5・AC6）。

**1回の対戦で、集計4項目＋勝率＋履歴1件が同時に更新される。** すべてに `aria-live` を付けると、1クリックで7項目以上が読み上げられ、ゲームとして使えなくなる。必要な情報は今回の結果（両者の手＋勝敗）に含まれており、集計値は利用者が能動的に読みに行ける。
