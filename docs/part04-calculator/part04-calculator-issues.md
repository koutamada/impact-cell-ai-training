# Part 4：計算機アプリ 論点整理（仕様確定前）

**本書は確定仕様書ではない。** 仕様書を作成する前に、依頼者の判断が必要な事項を洗い出したものである。

- 実装対象ディレクトリ（想定）：`apps/part04-calculator/`
- 仕様書パス（想定）：`docs/part04-calculator/part04-calculator-spec.md`

### 記法

| 記号 | 意味 |
|---|---|
| **[必須A]** | 課題文で明示されている要件 |
| **[必須B]** | 課題文には無いが、[必須A]を成立させるために決める必要がある事項 |
| **[追加候補]** | 課題文に無い機能。実装するかは依頼者の判断による |
| **★** | 依頼者の判断が必要（後から変えると影響が大きい） |
| **○** | 推奨案でよければ、この論点への回答は省略してよい |

**回答は「Q1: A案」「Q5〜Q9は推奨案で」のような形式で構わない。**

## 0. 全体に関する注意

電卓は画面が単純な一方で、**内部が状態機械（ステートマシン）である**点が Part 1〜3 と大きく異なる。

「同じボタンを押しても、直前に何を押したかで結果が変わる」のが電卓の本質である。

```
「5」を押す           → 表示 5
「+」を押す           → 表示 5（内部で加算待ち）
「3」を押す           → 表示 3（5を置き換えたのではなく、新しい入力）
「=」を押す           → 表示 8
ここで「3」を押すと？   → 8 に続けて 83 になるのか、新規入力の 3 になるのか
ここで「+」を押すと？   → 8 + の続きなのか、エラーなのか
```

**この分岐を仕様で定義しないと、実装者ごとに挙動が割れ、受入テストで判定できない。** 本書の3〜5章は、そのための論点である。

また、課題文の5条件は Part 1・2 と同程度の分量だが、**「入力内容のクリア」「連続した計算」「計算できないケース」はいずれも定義の幅が広く**、そのままでは実装に落ちない。

## 1. 課題文から直接読み取れる必須要件

| ID | 要件 | 課題文の該当箇所 |
|---|---|---|
| A1 | 数字入力と四則演算（＋ − × ÷）に対応する | 「数字入力と四則演算に対応する」 |
| A2 | 入力内容のクリアができる | 「入力内容のクリアと連続した計算ができる」 |
| A3 | 連続した計算ができる | 同上 |
| A4 | 過去に行った計算内容を履歴として表示する | 「過去に行った計算内容を履歴として表示する」 |
| A5 | キーボードから数字や演算子を入力できる | 「キーボードから数字や演算子を入力できる」 |
| A6 | ゼロ除算など、計算できないケースを適切に処理する | 「ゼロ除算など、計算できないケースを適切に処理する」 |
| A7 | ボタン操作でも入力できる | 「ボタン操作だけではなく、PCのキーボードからも」＝ボタン操作が前提 |

### 課題文から読み取れないこと

以下は課題文に**書かれていない**。「電卓なら普通あるから」という理由で確定してはならない。

- **小数**（「数字入力」としか書かれていない → Q1）
- **負数の入力手段**（減算はあるが、`-5` を直接入力する手段の有無 → Q2）
- **演算子の優先順位**（`2 + 3 × 4` の結果 → Q11）
- **Backspace**（1文字削除 → Q16）
- **履歴の永続化**（「表示する」までしか要求していない → Q19）
- **履歴の削除**（→ Q21）
- **±（符号反転）、%、√、括弧、メモリ機能**（→ 8章）

## 2. 必須要件を成立させるために追加で決める必要がある事項

課題文に無いが、これが無いと[必須A]が成立しない、または実装者ごとに挙動が割れる事項。

| ID | 事項 | なぜ必要か |
|---|---|---|
| B1 | **入力状態のモデル（状態機械）を定義すること** | 0章の通り、直前の操作によって同じキーの意味が変わる。定義しないと挙動が一意に決まらない |
| B2 | 保持する内部状態を定義すること | 「表示中の値」「確定した左辺」「保留中の演算子」「新規入力待ちか継続入力か」の4つが最低限必要 |
| B3 | 演算子の優先順位を決めること | A1が「四則演算」である以上、`2 + 3 × 4` が入力可能。結果が14か20かを決めないと実装できない |
| B4 | 「クリア」の対象範囲を決めること | A2の「入力内容のクリア」が、表示だけか計算途中の状態も含むかで挙動が変わる |
| B5 | 「連続した計算」の定義を決めること | A3の解釈が3通りあり得る（5章） |
| B6 | 履歴の記録タイミングと保持内容を決めること | A4の「計算内容」が式のみか結果込みかで表示が変わる |
| B7 | エラー状態と、そこからの復帰手段を定義すること | A6の「適切に処理する」の中身。復帰できないとアプリが操作不能になる |
| B8 | 表示可能な桁数と、超過時の挙動を決めること | 電卓は必ず桁あふれが起きる。未定義だと表示が崩れる |
| B9 | 浮動小数点誤差への対応範囲を決めること | `0.1 + 0.2 = 0.30000000000000004` がそのまま表示されると、電卓として成立しない |
| B10 | キーボードとボタンで**同一の内部処理**を通ること | A5とA7で挙動が食い違うと、同じ操作で異なる結果になる |

## 3. 数値入力に関する論点

### ★Q1. 小数を扱うか

| 案 | 内容 |
|---|---|
| **A案** | 小数を扱う（小数点ボタン `.` を設ける） |
| B案 | 整数のみ扱う |

**論点：** B案にすると、除算の結果をどうするかを別途決める必要がある（`7 ÷ 2` が 3.5 なのか、3 なのか、エラーなのか）。**除算があるのに整数のみとするのは、かえって仕様が複雑になる。**

**推奨：A案（小数を扱う）。** ただし小数点の重複入力（Q4）と誤差処理（Q27）の仕様が必要になる。

---

### ★Q2. 負数をどう扱うか

課題文には減算があるが、`-5` を直接入力する手段については記載がない。

| 案 | 内容 |
|---|---|
| **A案** | 直接入力の手段は設けない。負数は計算結果としてのみ現れる（`3 - 5 = -2`） |
| B案 | `±`（符号反転）ボタンを設ける |
| C案 | 数値入力の先頭で `-` を押したら負数の入力開始とみなす |

**推奨：A案。** `±` ボタンは課題文に無い機能の追加にあたる（8章の追加候補）。C案は「`-` が減算なのか符号なのか」の判定が状態依存になり、状態機械が一段複雑になる。

**A案の場合に決めること：** 計算結果が負数になった場合、その値を次の計算に使えること（`3 - 5 = -2` の後に `× 3 = -6`）。これは[必須B]として仕様に含める。

### ○Q3. 0で始まる入力

| # | 入力 | 推奨する表示 |
|---|---|---|
| 1 | `0` `0` `0` | `0`（複数の0を重ねない） |
| 2 | `0` `5` | `5`（先頭の0を置き換える） |
| 3 | `0` `.` `5` | `0.5` |
| 4 | 何も押していない初期状態 | `0` |
| 5 | `.` を最初に押す | `0.` とする（先頭に0を補う） |

**推奨：上記の通り。** 一般的な電卓の挙動であり、実装も単純。

---

### ○Q4. 小数点の重複入力

| 案 | 内容 |
|---|---|
| **A案** | 現在入力中の数値にすでに `.` が含まれる場合、2つ目の `.` を無視する |
| B案 | エラーにする |

**推奨：A案（無視）。** `3.14.` のような不正な値が生まれない。エラーにするのは過剰。

**あわせて決めること：** `5 + 3.` のように小数点で終わった状態で `=` を押した場合。**推奨：`3.` を `3` として計算する**（エラーにしない）。

---

### ○Q5. 入力できる最大桁数

| 案 | 内容 |
|---|---|
| **A案** | 上限を設ける（例：整数部12桁程度）。超過分の入力を無視する |
| B案 | 上限を設けない |

**推奨：A案。** B案だと、長押しや連打で無限に桁が増え、表示が崩れる（Q26と関連）。上限に達したら入力を受け付けない、という単純な処理でよい。

**具体的な桁数は依頼者の判断だが、12桁程度を推奨する。**

## 4. 演算と状態遷移に関する論点

**本章が Part 4 の中核である。**

### ★Q6. 演算子の連続入力

`5` `+` `-` `3` `=` のように、演算子を続けて押した場合。

| 案 | 内容 | `5 + - 3 =` の結果 |
|---|---|---|
| **A案** | 直前の演算子を**後から押したもので上書き**する | `2`（5 − 3） |
| B案 | 2つ目以降の演算子を無視する | `8`（5 + 3） |
| C案 | エラーにする | エラー |

**推奨：A案（上書き）。** 一般的な電卓の挙動であり、押し間違いを訂正できる。C案は利用者にとって不便。

---

### ★Q7. 「=」の後に数字を入力した場合

`5` `+` `3` `=`（表示 8）の直後に `7` を押す。

| 案 | 内容 | 結果の表示 |
|---|---|---|
| **A案** | 新しい入力の開始とみなし、表示を置き換える | `7` |
| B案 | 表示中の値に追記する | `87` |

**推奨：A案。** B案は前回の計算結果に数字がくっつくため、一般的な電卓の挙動から外れる。

---

### ★Q8. 「=」の後に演算子を入力した場合

`5` `+` `3` `=`（表示 8）の直後に `×` を押し、`2` `=` と続ける。

| 案 | 内容 | 結果 |
|---|---|---|
| **A案** | 表示中の結果（8）を左辺として計算を継続する | `16` |
| B案 | 新しい計算として扱い、左辺を 0 とする | `0` |

**推奨：A案。** これが課題文の**A3「連続した計算」の中核**にあたると解釈できる（Q9）。

---

### ★Q9. 「連続した計算」の定義

課題文の「連続した計算ができる」は、少なくとも3通りに読める。**どれを必須とするかを決める必要がある。**

| 解釈 | 例 | 説明 |
|---|---|---|
| **解釈1** | `5 + 3 = ` の結果に `× 2 =` を続けられる | 計算結果を次の計算の左辺として使える（Q8のA案） |
| **解釈2** | `5 + 3 × 2 =` のように `=` を押さずに演算子を続けられる | 演算子を押した時点で途中結果を確定する |
| 解釈3 | `=` を繰り返し押すと同じ演算が繰り返される（`5 + 3 =` の後に `=` で 11、さらに 14） | いわゆる「リピート計算」 |

**推奨：解釈1と解釈2を必須とし、解釈3は実装しない。**

- 解釈1・2は「連続した計算」の一般的な理解に含まれ、実装量も小さい
- 解釈3（リピート計算）は電卓ごとに挙動が異なり、課題文から読み取れない。**推奨：`=` の連続押下では表示を変化させない**（Q10と関連）

**解釈2を採る場合の具体的挙動：**

```
5 → 表示 5
+ → 表示 5（左辺=5、保留演算子=＋）
3 → 表示 3
× → この時点で 5+3 を計算し、表示 8（左辺=8、保留演算子=×）
2 → 表示 2
= → 8×2 を計算し、表示 16
```

**この方式（逐次計算）を採ると、Q11の優先順位の問題が自動的に解決する。**

---

### ★Q11. 演算子の優先順位

`2 + 3 × 4 =` の結果を決める必要がある。

| 案 | 内容 | 結果 |
|---|---|---|
| **A案** | **逐次計算**（電卓方式）。演算子を押した時点で左から順に計算する | `20` |
| B案 | 数式の優先順位（乗除を先に計算） | `14` |

**推奨：A案（逐次計算）。**

- 一般的な事務用電卓の挙動であり、Q9の解釈2と同じ実装で実現できる
- B案は式全体を保持し、優先順位を解析する処理が必要になり、実装量が大きく跳ね上がる
- 課題文は「四則演算に対応する」としか書いておらず、優先順位を要求していない

**A案を採る場合、仕様書に「本アプリは逐次計算方式であり、`2 + 3 × 4` は 20 となる」と明記する必要がある。** これを書かないと、受入時に「バグではないか」という疑義が生じる。

---

### ★Q10. 「5 + =」のような不完全な式

右辺が入力されていない状態で `=` を押した場合。

| 案 | 内容 | `5 + =` の結果 |
|---|---|---|
| **A案** | 右辺に**表示中の値をそのまま使う**（＝左辺と同じ値） | `10`（5 + 5） |
| B案 | 右辺を 0 として計算する | `5`（5 + 0） |
| C案 | 何もしない（`=` を無視する） | `5`（表示は変わらない） |
| D案 | エラーにする | エラー |

**推奨：C案（何もしない）。** 挙動が予測しやすく、受入テストで判定しやすい。A案は多くの実機電卓の挙動だが、利用者にとって直感的とは言いがたく、`5 + =` で 10 になる理由を説明できる必要がある。

**あわせて決めること：**

| 状況 | 推奨 |
|---|---|
| 何も入力せず `=` を押す | 何もしない（表示 `0` のまま） |
| `=` を続けて2回以上押す | 2回目以降は何もしない（Q9の解釈3を不採用とするため） |
| 演算子だけ押して `=`（例：`+ =`） | 何もしない |

### ○Q12b. 状態モデルの定義 [必須B] B1/B2

Q6〜Q11 の回答を、実装可能な状態モデルに落とす必要がある。仕様書には最低限、以下の内部状態を定義する。

| 状態変数 | 内容 |
|---|---|
| `currentInput` | 現在表示している数値（文字列で保持することを推奨。`0.` や先頭0の扱いが単純になる） |
| `accumulator` | 確定済みの左辺の値 |
| `pendingOperator` | 保留中の演算子（`null` あり） |
| `isNewInput` | 次の数字入力で表示を置き換えるか、追記するか |
| `hasError` | エラー状態かどうか（Q13） |

**この5つがあれば Q6〜Q11 の全パターンを表現できる。** 仕様書では、各ボタンを押したときの状態遷移を表形式で定義する予定である。

## 5. クリアとエラー処理に関する論点

### ★Q15. クリアの種類

課題文は「入力内容のクリア」としか書いていない。

| 案 | 内容 |
|---|---|
| A案 | `C` の1種類のみ（すべてリセット） |
| **B案** | `AC`（全消去）と `C`（現在の入力のみ消去）の2種類 |

| ボタン | 消すもの | 残るもの |
|---|---|---|
| `AC` | 表示・左辺・保留演算子・エラー状態のすべて | 履歴 |
| `C` | 現在入力中の数値のみ（表示を `0` に） | 左辺・保留演算子 |

**推奨：A案（`AC` 相当の1種類のみ）。**

理由：課題文の要求は「入力内容のクリア」1つであり、2種類は課題文に無い機能の追加にあたる。また `C` と `AC` の違いは利用者にも分かりにくく、受入テストの項目も倍増する。

**B案を選ぶ判断も妥当である。** その場合、上表の役割分担を仕様に明記する。

**[必須B] いずれの案でも決めること：** クリアで**履歴は消えない**こと（履歴の削除はQ21で別途扱う）。

---

### ○Q16. Backspace（1文字削除）の有無

課題文に記載がない。

| 案 | 内容 |
|---|---|
| **A案** | 実装する（ボタン＋キーボードの Backspace キー） |
| B案 | 実装しない |

**推奨：A案（実装する）。** 理由は、**Q24でキーボードの Backspace キーの割り当てを決める必要があるため**。キーが押されたときに何も起きないより、1文字削除が割り当てられている方が自然である。実装も数行で済む。

ただし厳密には課題文に無い機能であるため、依頼者の判断とする。

**A案の場合に決めること：**

| 状況 | 推奨挙動 |
|---|---|
| 1桁のみの状態で押す | `0` にする |
| `0` の状態で押す | 何もしない |
| `=` の直後に押す | 何もしない（結果を編集させない） |
| エラー状態で押す | 何もしない、またはエラー解除（Q13と統一する） |

### ★Q12. ゼロ除算時の表示 [必須A] A6

| 案 | 表示 |
|---|---|
| **A案** | `エラー` |
| B案 | `Error` |
| C案 | `Infinity`（JavaScriptの計算結果をそのまま表示） |

**推奨：A案またはB案。C案は採らない。** JavaScriptでは `5 / 0` が `Infinity`、`0 / 0` が `NaN` になるが、これらをそのまま表示するのは「適切に処理する」とは言えない。

**[必須B] エラーとする対象を明確にすること：**

| ケース | 判定 |
|---|---|
| `5 ÷ 0` | エラー |
| `0 ÷ 0` | エラー |
| `-5 ÷ 0` | エラー |
| 計算結果が `Infinity` / `-Infinity` になる（桁あふれ） | エラー（Q26と関連） |
| 計算結果が `NaN` になる | エラー |

**推奨：計算結果が有限の数値でない場合はすべてエラーとする**（`Number.isFinite()` による一括判定）。ゼロ除算だけを個別に判定するより、漏れがなく実装も単純になる。

---

### ★Q13. エラー状態からの復帰方法 [必須B] B7

エラー表示後、どうすれば通常状態に戻れるかを決める必要がある。**決めないとアプリが操作不能になる。**

| 案 | 内容 |
|---|---|
| **A案** | クリアボタン（`AC`）でのみ復帰する。他のキーはすべて無視する |
| B案 | 任意のキー入力で復帰し、その入力から新しい計算を始める |

**推奨：A案。** 挙動が明確で、受入テストでも判定しやすい。「エラー中は `AC` 以外効かない」という単純なルールになる。

**A案の場合、[必須B] として以下を仕様に含める：**

- エラー状態であることが画面上で分かること
- エラー中は数字・演算子・`=` を押しても何も起きないこと
- エラー中もキーボード入力は同様に無視されること
- エラーになった計算を履歴に記録するか（→ Q17）

## 6. 履歴に関する論点

### ★Q17. 履歴に何を表示するか [必須A] A4

| 案 | 表示内容 | 例 |
|---|---|---|
| A案 | 結果のみ | `8` |
| **B案** | 式と結果 | `5 + 3 = 8` |
| C案 | 式・結果・時刻 | `5 + 3 = 8（12:34）` |

**推奨：B案。** 課題文の「計算内容を履歴として表示する」は、結果だけでは「計算内容」とは言いがたい。時刻は課題文に無い要素であり、不要。

**[必須B] あわせて決めること：**

| 論点 | 推奨 |
|---|---|
| 逐次計算での記録単位 | `5 + 3 × 2 =` は**1件**として `5 + 3 × 2 = 16` と記録する。途中の `5 + 3 = 8` を別途記録しない |
| 記録するタイミング | **`=` を押して計算が確定したときのみ** |
| エラーになった計算 | **履歴に記録しない**（推奨）。または `5 ÷ 0 = エラー` として記録する。要判断 |
| 表示順 | 新しいものが上（推奨） |

**記録タイミングを `=` のみとする理由：** 演算子を押すたびに途中結果を記録すると、`5 + 3 × 2 =` で3件の履歴が生まれ、利用者の意図とずれる。

### ○Q24. Enter / Escape / Backspace の扱い

**推奨：Q23の表の通り**（Enter=`=`、Escape=クリア、Backspace=1文字削除）。

**[必須B] 注意点：** ボタンにフォーカスがある状態で `Enter` を押すと、**ブラウザの既定動作でそのボタンがクリックされる**。`Enter` に `=` を割り当てると、「数字ボタンをクリックした後に Enter を押すと、`=` ではなくその数字が再入力される」という不具合が起きる。

**対策：** `Enter` の既定動作を抑止する、またはボタンを押した後にフォーカスを外す。**この点は仕様書に明記する必要がある。**

### ★Q26. 長い数値・桁あふれの表示 [必須B] B8

| 論点 | 推奨 |
|---|---|
| 表示できる最大桁数 | 12桁程度（Q5の入力上限と合わせる） |
| 計算結果が表示桁数を超える | **要判断。** 下記の案から選ぶ |
| 小数の最大桁数 | 一定桁で四捨五入する（Q27と関連） |
| 桁区切り（`1,234,567`） | **推奨：入れない。** 課題文に無く、小数点との併用で実装が煩雑になる |

**計算結果が桁数を超えた場合の案：**

| 案 | 内容 | 例（`999999999999 × 999999999999`） |
|---|---|---|
| **A案** | エラーとして扱う | `エラー` |
| B案 | 指数表記に切り替える | `9.99999999998e+23` |
| C案 | そのまま表示し、文字を縮小・折り返す | 表示が崩れる可能性 |

**推奨：A案（エラー扱い）。** Q12の「有限でない値はエラー」と統一でき、判定が単純になる。B案は指数表記の桁数調整が必要で、実装量が増える。

**[必須B] 表示領域の堅牢性：** 上限桁数まで表示しても、レイアウトが崩れず、横スクロールが発生しないこと（フォントサイズの自動縮小、または固定幅での省略）。

### ★Q27. 浮動小数点誤差への対応範囲 [必須B] B9

JavaScriptでは `0.1 + 0.2` が `0.30000000000000004` になる。これをそのまま表示すると電卓として成立しない。

| 案 | 内容 | 実装量 |
|---|---|---|
| **A案** | 計算結果を**一定の有効桁数で丸めて表示する**（例：`Number(result.toPrecision(12))`） | 小 |
| B案 | 内部で整数化して計算する（小数点以下の桁数を揃えて整数演算し、最後に戻す） | 中 |
| C案 | 対応しない（そのまま表示する） | なし |

**推奨：A案。** 1行の処理で `0.1 + 0.2 = 0.3` を実現でき、トレーニング課題として必要十分である。

**A案の限界を仕様書に明記すること：** 有効桁数を超える精度は保証されない。**「本アプリは任意精度演算を目的とせず、一般的な電卓として妥当な範囲の精度を提供する」**と書いておく。これを書かないと、極端な入力での誤差を不具合と誤認する。

**C案は採らない。** A6の「計算できないケースを適切に処理する」の趣旨から外れる。

**[必須B] あわせて決めること：** 丸めた結果の末尾の `0` を削る（`0.30` ではなく `0.3` と表示する）。
